# 병동 코디네이터: 병상 배정·입퇴원 일정 에이전트 (설계안 v2, 근거 반영)

> 가상 병원 데이터로 만드는 개인 프로젝트. 실제 병원 데이터 사용 없음.
> 현장 절차와 기준은 아래 공개 자료에서 가져옴. 자료에 없는 부분은 "가정"으로 표시.

## 1. 문제
- 병상 배정 담당자가 퇴원 예정, 병동 현황, 입원 예정, 응급실 대기를 매번 여러 화면에서 모아 판단
- 예약·변경·취소 요청이 전화와 메신저로 흩어져 들어옴
- 의사 일정은 별도 시스템이라 "지금 김교수 가능?"을 사람이 묻고 확인 (소장님 언급 사례, 가정)

## 2. 사용자와 시나리오 (MVP)
| # | 사용자 | 요청 | 처리 |
|---|---|---|---|
| S1 | 원무팀 | "내과 72세 남, 내일 입원, 결핵 의심이라 격리" | 배정 에이전트가 규칙으로 후보 3개와 근거 제시 → 담당자 승인 → 확정 |
| S2 | 원무팀 | (5분 주기 자동) 오늘 입원 예정 전체 | 배정 가능 건은 제안, 불가 건은 사유와 함께 담당자 알림 |
| S3 | 병동 간호사 | "내일 정규 퇴원 확정된 환자랑 병상 비는 시간" | 퇴원 에이전트가 퇴원 등록 목록과 병상 가용 예상 제시 |
| S4 | 원무팀·간호사 | "김교수 오늘 오후 회진 시간?" | 일정 에이전트가 권한 확인 후 응답 |
| S5 | 원무팀 | 정오 전 병실 부족 예상 | 입원일 변경 연락 대상 목록 생성 (연락은 사람이) |

## 3. 구조
```
채팅·대시보드 (Streamlit)
  └ FastAPI
      └ 오케스트레이터 (LLM: 요청 분류, 자유 서술을 조건으로 변환, 에이전트 호출, 응답 합성)
          ├ 배정 에이전트   → 규칙 필터 + 점수 (OR-Tools 또는 직접 구현). LLM은 설명만
          ├ 퇴원 에이전트   → 퇴원 등록 기반 병상 가용 예상 (MVP는 규칙, 이후 재원 기간 예측 모델)
          ├ 일정 에이전트   → 의료진 일정 조회, 빈 시간, 충돌 검사
          └ 정책 가드       → 역할별 권한, LLM 전송 전 가명, 감사 로그
      └ 도구 계층 (MCP 서버)
          get_bed_status / get_admission_queue / propose_assignment / confirm_assignment
          get_discharge_list / get_schedule / notify_staff
          └ PostgreSQL (트랜잭션, 병상 중복 배정 차단) + 온톨로지 스키마 (YAML)
```
- 쓰기 작업은 전부 제안 상태 → 사람 승인 → 트랜잭션 확정
- 배정 결과는 숫자와 규칙 근거로만 결정, LLM이 병상을 고르지 않음

## 4. 온톨로지와 DB
- 클래스 (FHIR 이름 기준): Patient, Encounter(입원), Location(병동·병실·병상), Practitioner(의료진), Organization(진료과), Schedule·Slot·Appointment(일정), Task(퇴원·병상 변경)
- 관계: Patient–Encounter–Location(병상)–Location(병실)–Location(병동)–Organization(진료과) / Practitioner–Organization / Practitioner–Schedule–Slot
- 배정 제약 (서울아산 기준에서 가져옴): 진료과 병동 우선, 성별 병실, 격리(음압·1인실), 중증도, 수술 일정, 동명이인 같은 병실 금지, 선호 병실, 예약 순서
- 왜 나누나: 확정에는 트랜잭션이 필요 → 관계형 DB / 에이전트가 읽는 도메인 지식과 제약 → 온톨로지 YAML에서 도구 설명과 검사 코드 생성 / 관계 추론이 늘면 그래프 DB로 확장

## 5. 가상 데이터
- 300병상 가정 종합병원: 병동 8개(진료과 병동 6, 간호간병 1, 중환자 1), 병실 최대 4병상, 음압격리 2실
- 환자 2주치 입원 예약, 응급 입원, 정규 퇴원, 병상 변경 요청 생성
- 원무팀 전달사항은 자유 서술 문장 200개 생성 (예: "보호자 상주 원함, 창가 자리 희망")
- 전부 가명, 실제 병원 데이터 없음

## 6. 평가
- 시나리오 50개: 정상 30, 함정 20 (격리 환자 다인실 요청, 동명이인, 권한 없는 일정 조회, 동시 배정, 병상 부족)
- 지표: 자동 배정률, 기준 위반 0건, 중복 배정 0건, 사람 확인 요청 비율, 자유 서술 조건 변환 정확도, DB에 없는 사실 응답 비율, 요청당 응답 시간과 비용
- 같은 시나리오 3회 반복으로 변동 폭 확인
- 병원 발표 수치(90.8% 등)와 직접 비교하지 않음 (데이터와 조건이 다름)

## 7. 범위 밖 (연결 지점만)
- 피지컬 AI: Task(병상 정리, 이송)를 로봇·장비가 구독하는 이벤트 큐로 정의
- 재원 기간 예측: MVP는 퇴원 등록 기반 규칙, 이후 가명 데이터로 학습한 예측 모델

# v3 토론 결론 (2026-11-08, 병원 현장 실무자, AI-DD 연구소장, 시니어 엔지니어 2라운드)

## 합의된 수정
1. 축 이동: 병상 배정 챗봇 → 퇴원부터 병상 준비 완료까지 턴어라운드 관제 (배정은 이미 상용화된 기능, 실무 병목은 퇴원 결정 후 퇴원약·수납·퇴실·청소까지의 시차)
2. 원장은 HIS: HIS 어댑터(목업)에서 읽기만, 확정 버튼은 "HIS 전송 대기", 감사 로그
3. 격리는 주치의 격리 오더 값으로 입력 (LLM 해석 대상 아님), 교수 회진 시나리오 삭제
4. 실행은 단일 에이전트 + 도구 + 이벤트 핸들러. Task마다 담당(약제, 원무, 청소)을 붙여 하위 에이전트·로봇으로 교체할 경계만 남김
5. 컷: MCP, 멀티에이전트, OR-Tools, pySHACL, 회귀 모델 → 연결 지점으로만 문서화
6. 병상 상태 코드: FHIR Location.operationalStatus (O 사용중, H 청소중, U 빈 병상, C 폐쇄)
7. 용어: 전동·전실, 간호·간병통합서비스 병동

## MVP (시뮬레이션 시계, 4시간)
| 파일 | 내용 | 시간 |
|---|---|---|
| gen_data.py | 가상 퇴원 30건, 단계별 지연 분포 | 40분 |
| events.py | 퇴원 확정 → 퇴원약 → 수납 → 퇴실 → H → 청소 Task → U → 배정 제안 이벤트 연쇄 | 80분 |
| monitor.py | 단계별 기준 시간 초과 탐지, 담당자 알림 | 40분 |
| forecast.py | 15시 가용 병상 추정: 기준선(퇴원 확정 = 즉시 가용) vs 단계별 중앙값 합산 | 40분 |
| app.py | Streamlit 타임라인, 알림, 승인 화면. LLM은 알림 요약과 자연어 질의만 | 40분 |

## 평가
- 15시 가용 병상 수 MAE (기준선 대비), 지연 탐지 정밀도·재현율, 제약 검사 단위 테스트
- 표기: "합성 데이터 기준 추정". "예측 모델", "자동 배정률" 표현 금지, 병원 발표 수치와 나란히 두지 않음

## 시연 장면
가상 09시 퇴원 확정 3건 → "11:40 병상 준비 예상, 정오까지 2병상 부족" → 수납 지연 1건 담당자 알림, 청소 Task 앞당김 → 청소 완료 이벤트 → 대기 환자 배정안이 승인 화면에 표시. 아무도 묻지 않아도 연쇄가 돈다.
