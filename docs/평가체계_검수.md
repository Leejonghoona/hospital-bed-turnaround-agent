## 1. 작업 방식 검수

### 1-1. 평가 하네스가 5단계에 있는 것은 늦다
- **"합격"의 정의가 구현보다 늦게 나온다.** 2~4단계(저장소, 사가, 게이트웨이)의 테스트를 그 단계 코드와 함께 쓰면, 테스트가 설계 요구가 아니라 구현의 가정을 굳힌다. 생성기 테스트가 이미 그렇다. `len(delayed) == guardian_delay_count` 같은 단언은 생성기가 자기 설정을 따르는지만 보고, 평가에 쓸 만한 데이터인지는 보지 않는다.
- **2단계에서 정할 것이 평가 요구에 묶여 있다.** 재생 평가를 하려면 이벤트마다 "실제로 일어난 시각"과 "시스템이 알게 된 시각"을 따로 가져야 한다. 둘이 없으면 미래 정보를 미리 보는 누수(lookahead)를 검사할 수 없다. 지금 생성기는 `DischargeTimeline`에 하루 전체의 실제 시각을 한 번에 담아 둔다. 이것을 그대로 저장소에 넣으면 에이전트 도구가 13시 퇴실 시각을 9시에 볼 수 있다. 이 결정은 5단계에 가서 되돌리기 어렵다.
- **비교 기준선이 단계 목록에 없다.** "에이전트 없음(기존 방식)"과 "규칙 모드(LLM 없음)" 두 기준선이 있어야 LLM이 실제로 무엇을 더하는지 잴 수 있다. 설계 문서는 규칙 모드를 LLM 장애 시 대체 경로로 정해 두었는데, 9단계 어디에도 들어 있지 않다.

### 1-2. 단계 순서가 서로 의존한다
- 4단계 게이트웨이의 "SHACL 재검사"는 6단계 온톨로지 없이는 돌 수 없다. 4단계 전에 최소한의 SHACL 제약 모양(격리, 성별, 동명이인, 종말소독)을 먼저 만들거나, 검사기를 갈아 끼울 수 있는 인터페이스로 두어야 한다.
- 교체 가능한 LLM 인터페이스와 가짜 LLM이 독립된 단계로 없다. 5단계 하네스에서 "모델별 정답 일치율"을 재려면 인터페이스가 먼저 있어야 한다.
- 8단계 몬테카를로는 생성기 분포만 있으면 지금도 만들 수 있다. 다만 2절의 순환 문제 때문에 평가 설계를 먼저 끝낸 뒤 만들어야 한다.

### 1-3. "테스트 먼저, 작게 커밋"의 한계
- 단위 테스트를 먼저 쓰는 것은 좋다. 하지만 같은 작성자(또는 같은 AI 에이전트)가 테스트와 코드를 같은 맥락에서 쓰면 오해도 둘 다에 똑같이 들어간다. 그래서 두 층으로 나눈다.
  - **인수 시나리오**: 설계 문서에서 바로 끌어오고, 구현 전에 확정해 고정한다. 처음에는 실패 상태(xfail)로 둔다.
  - **단위 테스트**: 지금처럼 단계마다 쓴다.
- 커밋마다 "점수판 변화"(통과한 시나리오 수, 안전 위반 건수)를 남기면 작은 커밋이 실제로 목표를 향해 가는지 보인다.

### 1-4. 평가표는 언제, 무엇부터 만드나: 지금, 2단계보다 먼저
만드는 순서는 다음과 같다.
1. 지표 정의(계산식과 분모)
2. 시나리오와 정답 라벨 형식
3. 독립 불변 조건 검사기(생성기, SHACL과는 별도로 짠 순수 파이썬 검사기)
4. 점수판과 기준선 점수

이 네 가지를 이후 단계마다 숫자가 움직이는 틀로 쓴다.

## 2. 평가 체계의 빈틈과 보완안

| # | 빈틈 | 왜 문제인가 | 보완안 |
|---|---|---|---|
| G1 | 턴어라운드 개선이 순환 논리 | 에이전트 효과는 "퇴실 즉시 청소 요청" 같은 가정으로만 생긴다. 기준선의 청소 요청 지연(중앙값 20분)을 0으로 바꾸면 개선 폭은 생성기가 정한 그대로 나온다 | 개입 가정에 ID를 붙여 DECISIONS.md에 명시한다. 결과를 "기계적으로 보장되는 효과"와 "가정에서 나온 효과"로 나누고, 가정값을 0.5배와 2배로 바꿔 보는 민감도 표를 붙인다. 운영 지표는 PoC 성공 기준에서 빼고 참고 지표로 둔다 |
| G2 | 정오 가용 병상 P10~P90 구간 포함률이 자동으로 맞음 | 몬테카를로가 생성기와 같은 로그정규 분포를 쓰면 포함률은 정의상 약 80%가 나온다 | 홀드아웃은 분포를 일부러 틀리게 만든 생성기(P90 +30%, 다른 분포 형태, 보호자 지연 비율 변화)로 만든다. 기준선을 둘 둔다: "퇴원 확정 즉시 빈다"(약한 기준선)와 "단계별 중앙값 합"(강한 기준선). 예측 시점(전날 17:00, 당일 09:05)과 그때 쓸 수 있는 정보를 지정한다 |
| G3 | 표본이 너무 적음 | 시드 하나에 격리 퇴실 3건, 미등록 2건이라 "종말소독 누락 0건"이나 "예정 누락 감지율"은 통계적으로 의미가 없다 | 안전 지표는 시드 0~199를 돌려 쓰고 분모와 95% 신뢰 상한을 함께 적는다. 예: 600건에서 0건이면 3의 규칙으로 상한 0.5% |
| G4 | "오분류율"이 비대칭 위험을 가림 | 검토 등급 사례를 자동으로 보내는 것(위험)과 자동 사례를 검토로 보내는 것(부담)이 한 숫자에 섞인다 | 3×3 혼동행렬(자동, 병동 확인, 담당 검토). 등급을 낮춘 오류는 0건을 지킬 선, 높인 오류는 사람 부담 지표. 원인(추출, 입력 누락, 정책)도 나눠 센다 |
| G5 | "배정 기준 위반"의 층이 모호 | 게이트웨이가 막은 위반 제안과 실제로 실행된 위반이 구별되지 않는다 | 실행된 위반 0건(시스템 안전)과 제안된 위반 비율(에이전트 품질)로 나눈다. 중단 기준은 실행된 위반에만 건다 |
| G6 | "정답 일치율"이 무엇의 일치인지 미정 | 조건이 같은 병상이 여럿이면 정답이 하나가 아니다 | 라벨에 "허용 병상 집합"과 "금지 행동"을 둔다. 확인 등급, 행동 유형, 병상(집합 포함 여부)을 따로 채점한다 |
| G7 | 반복 일관성이 가짜 LLM에서는 자동 100% | 결정적 가짜 LLM으로 5회를 돌리면 아무것도 재지 않는다 | pass^5는 실제 모델에서만 보고하고, 가짜 LLM에는 "해당 없음"으로 표시한다 |
| G8 | 가짜 LLM이 정답표가 될 위험 | 가짜 LLM이 시나리오 ID나 정답을 보고 답하면 파이프라인 평가가 무의미해진다 | 가짜 LLM은 관찰값만 보는 규칙 기반으로 짠다. `src/`에 시나리오 ID 문자열이 들어가면 실패하는 테스트를 둔다 |
| G9 | 추출 평가 문장 200개의 출처가 없음 | 생성기 템플릿으로 만들면 정규식으로도 풀리고 가짜 LLM이 과적합한다 | 생성기와 독립적으로 사람이 쓰거나, 비교 대상이 아닌 모델로 초안을 만든 뒤 사람이 검수한다. 개발용 100, 홀드아웃 100. "틀린 값"과 "비워 둠(null)"을 구별하고 틀린 값을 더 무겁게 센다 |
| G10 | 인젝션 지표의 비교 대상이 없음 | "판단이 바뀐 횟수"는 공격 문장이 없을 때와 비교해야 정의된다 | 공격 문장 유무로 짝지은 판을 돌려 결정이 다른 쌍을 센다. 격리 언급은 등급을 올리기만 하고 내리지 못한다는 단조성 테스트를 둔다 |
| G11 | 사람 응답이 모델링되지 않음 | 입실 구간은 책임간호사 회신과 원무 확정에 달려 있는데 생성기에 없다 | 합성 응답자(회신 지연 분포, 수용 불가 확률)를 가정으로 명시하고, 입실 구간 수치는 이 가정에서 나온 값이라고 표기한다 |
| G12 | 생성기가 평가 입력을 다 만들지 못함 | 자유 서술, 같은 병실에 남는 재원 환자, Appointment·Schedule(13:00 수술 질문), 이벤트 잡음(중복, 순서 뒤바뀜, 완료 신호 누락)이 없다 | 시나리오 고정 데이터로 보강한다. 생성기를 계속 늘리기보다 시나리오 쪽에서 채운다 |
| G13 | 라벨 검수에서 같은 모델 계열 편향 | 설계 표는 "Opus 5.5가 회귀 정답 라벨 검수 보조"인데 비교 대상에 Haiku 5.5와 Sonnet 5.5가 있다 | 라벨 확정은 사람이 하고, LLM은 예외 사례 아이디어에만 쓴다. 라벨마다 출처(설계 규칙, 작성자, 작성 커밋)를 남긴다 |
| G14 | 자율화 승격 기준값을 같은 데이터로 조정 | 30개로 유형별 기준값을 정하면 과적합이다 | 기준값은 개발용으로만 조정하고 홀드아웃에서 확인한다. 유형별 표본 수를 함께 적고, 승격 기능은 "정책 절차 시연"이라고 명시한다 |
| G15 | 평가 자체의 민감도를 모름 | 테스트가 통과해도 문제를 잡을 수 있는 테스트인지 알 수 없다 | 뮤턴트 검사: 게이트웨이 재확인이나 종말소독 강제를 하나씩 일부러 끄고 최소 1개 시나리오가 실패하는지 확인한다 |

## 4. 진행 방식 제안

- **커밋 1, 평가 골격과 라벨 고정**: DECISIONS.md 기록, 시나리오 스키마, 라벨 30개, 스키마 테스트
- **커밋 2, 독립 검사기와 점수판**: SHACL과 별도로 짠 불변 조건 검사기, 위반을 넣은 고정 데이터 테스트, 에이전트 없음 기준선, 점수판, 시나리오 ID 누수 테스트
- **커밋 3, 2단계 이벤트 저장소**: 추가만 하는 기록, 사례 ID와 멱등 키 UNIQUE, `occurred_at`과 `observed_at` 분리, 잡음 주입 옵션, 미래 이벤트 비노출 테스트
- **데이터 분리**: 개발용은 시드 0~199와 dev 시나리오 30개. 홀드아웃은 봉인 시드(10000 이후), 분포를 바꾼 설정, 예외가 겹치는 변형. 마일스톤(4단계, 7단계 끝)에만 돌리고 실행 횟수를 기록한다. AI 코딩 에이전트가 홀드아웃 라벨을 읽는 것도 누수이며, 읽기 차단 설정은 사용자가 결정할 사항이다.
- **라벨**: 생성기는 입력만 만들고 정답을 만들지 않는다. 라벨은 설계 규칙에서 도출해 구현 전에 고정하고, 고칠 때는 사유를 DECISIONS.md에 적는다. 판정 검사기는 평가 대상 코드와 다른 구현이어야 한다.
- **RESULTS.md**: 실행마다 결과 JSON을 기계가 만들고, 요약 한 줄(날짜, 커밋, 시나리오 세트 해시, 데이터 분리, LLM, 정책 버전, 안전 지표 건수/분모, 통과 수/30, 운영 지표와 가정 ID)을 스크립트로 추가한다.

## 5. 우선순위 Top 5 권고

1. 평가 골격을 지금, 2단계보다 먼저 만든다. 시나리오 스키마, 라벨 30개, 독립 검사기, 점수판, 두 기준선(에이전트 없음, 규칙 모드).
2. 이벤트 저장소에 "발생 시각"과 "인지 시각"을 넣고 미래 정보 누수 테스트를 2단계 합격 조건으로 삼는다.
3. 생성기와 평가가 같은 가정을 쓰는 순환을 끊는다. 개입 가정에 ID를 붙이고 민감도를 보이며, 정오 병상 MAE와 구간 포함률은 분포를 바꾼 홀드아웃에서만 보고한다.
4. 안전 지표를 비대칭이면서 통계적으로 의미 있게 다시 정의한다. 등급을 낮춘 오분류 0건과 실행된 위반 0건을 지킬 선으로 두고, 시드를 돌려 분모와 신뢰 상한을 붙이며, 뮤턴트로 평가가 실제로 문제를 잡는지 검증한다.
5. 라벨 독립성과 홀드아웃 봉인을 지킨다. 사람이 라벨을 확정하고 출처를 남기며, Claude 계열을 라벨 검수에 쓰지 않고, 가짜 LLM은 관찰값만 보게 하고, 시나리오 ID 하드코딩을 검사하고, 홀드아웃 실행 횟수를 기록한다.
