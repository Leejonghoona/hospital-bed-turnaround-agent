# 설계 결정 기록

설계 문서와 다르게, 또는 설계 문서보다 구체적으로 정해야 할 때 코드보다 먼저 이유를 적는다.

## 2026-11-08 LLM 모델 선정과 배치

**맥락**: 설계 문서는 "운영은 병원 서버의 작은 LLM, 외부 모델 비교는 개발 단계에서 가상 데이터로만"까지만 정해 두었다. 어떤 모델을 어느 역할에 쓰는지, Claude 같은 외부 API를 어디까지 허용하는지는 정해지지 않았다.

**결정** (설계 문서 `#model` 섹션에 표와 근거)
- 역할을 추출 LLM, 계획 에이전트, 질의 응답 셋으로 나누고 역할별로 모델을 고른다. 추출은 추론 모드를 끈 소형 모델, 계획은 추론 모드를 켠 중형 모델.
- 선정 순서: 데이터 위치(관문) → 라이선스(관문) → 한국어 추출 정확도, 도구 호출 유효율, 인젝션 저항, 반복 일관성, 지연과 장비. 3번부터는 재생 평가 하네스로 측정한다.
- 기본값은 결정적 가짜 LLM. 개발 단계에서 `ANTHROPIC_API_KEY`가 있으면 Claude Haiku 5.5(추출), Claude Sonnet 5.5(계획)를 상한 기준선으로 쓴다.
- 운영 1안은 원내 오픈 가중치: 추출 Gemma 4 26B 또는 gpt-oss-20b, 계획 gpt-oss-120b. 장비가 되면 K-EXAONE, 한국어 보강은 Solar Open 100B. 최종 조합은 하네스 결과로 정한다.
- 운영 2안은 Bedrock 서울 단일 리전 Claude(계획만). 추출은 어떤 경우에도 원내 모델이 맡고, 클라우드에는 추출된 코드값과 사례 ID만 보낸다.

**이유**
- Claude 직접 API는 `inference_geo`가 `us`, `global`뿐이고 작업공간 저장 위치는 미국뿐이다(공식 문서, 2026-11 확인). 환자 데이터를 보내면 개인정보보호법 제28조의8 국외 이전과 민감정보 별도 동의 문제가 생기고, 병원 망분리와도 맞지 않는다.
- 하루 퇴원 200건 가정에서 API 비용은 월 약 $44(Haiku 5.5, GPT-6 Luna)~$1,770(Opus 5.5, Gemini 4 Carbon) 수준이라 비용은 결정 요인이 아니다.
- Artificial Analysis 지능 지수 v5.0.1(2026-11-08 조회)은 API 모델만 측정돼 있고(Gemini 4 Carbon 60.0, Opus 5.5 59.1, Sonnet 5.5 54.5, Haiku 5.5 36.5), 원내 후보는 대부분 N/A다. 그래서 원내 후보는 같은 사이트의 IFBench(추출 대리 지표)와 τ²-Bench(계획 대리 지표)로 1차 선별했다: 추출은 Gemma 4 26B 72%, gpt-oss-20b 65%, 계획은 K-EXAONE 74%, gpt-oss-120b 66%.
- EXAONE 4.0은 라이선스가 NC(연구·교육용)라 데모 비교에만 쓴다. K-EXAONE은 병원 서버 규모를 넘는다.

**확인이 더 필요한 것**
- Bedrock 서울 단일 리전 Claude 제공 범위(2차 보도 기준 Opus 5, Sonnet 5)와 가격: AWS 원문 확인.
- Solar Open 100B 가중치 라이선스(Upstage Solar License)의 상업 이용 조건.
- Solar Open2 250B, Solar Open 100B는 Artificial Analysis 측정치가 없음. 하네스로 직접 측정.
- K-EXAONE 라이선스(K Exaone)의 상업 이용 조건.

## 2026-11-08 합성 데이터의 기간과 단계 모델

**맥락**: 설계는 "병동 2개, 병상 24개, 퇴원 30건, 입원 대기 15건"만 정했다. 병상 24개에서 하루에 퇴원 30건은 나올 수 없다.

**결정**
- 퇴원 30건을 평일 5일(하루 6건)에 나눈다. 설계 시연 장면의 "내일 정규 퇴원 6건"과 맞춘다. 같은 날 같은 병상의 퇴원은 1건만 둔다. 다음 퇴원 전까지 그 병상은 대기열 밖 입원(예약 입원, 전동)으로 다시 찬다고 가정하고, 그 입원은 생성하지 않는다.
- 입원 대기 15건은 같은 5일에 나눈다. 배정과 입실 시각은 생성하지 않는다. 그건 계획 에이전트와 도구가 정한다.
- 예외 건수(보호자 지연, 청소 지연, 퇴원 예정 미등록, 입원 취소, 격리 퇴실)는 확률이 아니라 정확한 개수로 넣는다. 회귀 시나리오와 테스트가 항상 같은 수의 예외를 보게 하려는 것이다.
- 단계 소요시간은 로그정규분포로 뽑는다. 파라미터는 중앙값과 P90으로 정의하며, 설계값(가정)이다. 실제 병원 측정치가 아니다.
- 퇴실 전 단계 순서: 퇴원 오더 확정 → 퇴원약과 퇴원 교육을 병행 → 퇴원약 뒤 진료비 심사와 수납 → 보호자 도착 → 퇴실. 퇴실 시각은 수납 완료, 교육 완료, 보호자 도착 중 가장 늦은 시각에 퇴실 준비 시간을 더한 값이다.
- 기존 방식의 청소 요청 지연(퇴실 뒤 병동이 전화하기까지)도 분포로 따로 뽑는다. 에이전트의 "퇴실 즉시 요청"과 비교할 기준선으로 쓴다.

## 2026-11-08 평가 골격을 2단계보다 먼저 만든다

**맥락**: CLAUDE.md 구현 우선순위는 평가 하네스를 5단계에 둔다. 독립 검수(`docs/평가체계_검수.md`)에서 지적이 나왔다. 합격 정의가 구현보다 늦게 나오면 테스트가 구현의 가정을 굳히고, 2단계 이벤트 형식이 미래 정보 누수 검사를 못 하는 모양으로 굳을 수 있다. 사용자가 순서 변경을 승인했다.

**결정**
- 순서를 1 → **1.5 평가 골격** → 2 → 3 → … 로 바꾼다. 1.5에서 만드는 것:
  - 평가표: `docs/평가표.md`
  - 시나리오 라벨 스키마: `src/turnaround/evaluation/scenario.py`
  - 결과 수준 라벨 30개: `evals/scenarios/dev/`
  - 생성기와 별개로 짠 안전 불변 조건 검사기: `src/turnaround/evaluation/invariants.py`
  - 이후 커밋에서 점수판과 에이전트 없음 기준선
  - 나머지 하네스(재생 실행, 모델 비교)는 계속 5단계
- 라벨 30개는 지금 결과 수준(상황, 확인 등급, 필수·금지 행동, 허용 병상)까지만 고정한다. 이벤트 순서와 시각은 2단계 이벤트 형식이 정해진 뒤 채운다.
- 라벨은 Claude가 설계 문서 규칙에서 초안(`status: draft`)을 쓰고, 사용자가 검토해 `approved`로 바꾼다. Claude 계열 모델을 라벨 검수에 쓰지 않는다. 설계 표의 "Opus 5.5 회귀 정답 라벨 검수 보조"는 철회한다.
- 2단계 이벤트 저장소는 이벤트마다 `occurred_at`(발생)과 `observed_at`(인지)을 따로 두고, 미래 정보 누수 테스트(S4)를 합격 조건으로 둔다.
- 비교 기준선은 둘이다: 에이전트 없음, 규칙 모드(LLM 없음). 규칙 모드는 설계 문서에 이미 있는 LLM 장애 경로라 새 범위가 아니다.
- 홀드아웃 봉인 정책: 시드 10000 이후와 분포를 바꾼 설정. 마일스톤에만 만들고 실행한다. AI 에이전트의 홀드아웃 읽기 차단 설정은 사용자 결정 사항이라 적용하지 않았다.

**개입 가정 ID** (운영 지표 O1은 이 ID와 0.5배·2배 민감도를 함께 보고한다)
- AS-01: 에이전트는 퇴실 즉시 청소를 요청한다(기존 요청 지연 → 0분). 결정적 코드가 보장하는 효과.
- AS-02: 대기 정보를 공유하면 수납 대기 기준 초과 건의 수납 시간이 줄어든다. 감소율은 가정값이라 정해지기 전까지 0으로 둔다.
- AS-03: 사전 매칭이 있으면 병상 준비 완료부터 병동 문의까지 지연이 사라진다. 병동 회신 지연은 합성 응답자 분포를 따른다(G11, 2단계 이후 정의).
- AS-04: 보호자 도착 예정 갱신을 반영하면 준비 시각 재추정이 갱신 시점에 일어난다. 실제 도착은 바뀌지 않는다.

## 2026-11-08 2단계 이벤트 저장소의 시간 의미론과 사례 ID

**결정**
- 이벤트마다 `occurred_at`(현실에서 일어난 시각)과 `observed_at`(시스템이 알게 된 시각)을 둔다. `observed_at < occurred_at`은 거부한다. 조회의 `as_of`는 `observed_at` 기준이다. 판단 시점보다 늦게 인지된 이벤트는 보이지 않는다(평가표 S4).
- 사례 ID는 지금 퇴원 사례는 퇴원 ID(`SYN-D…`), 입원 대기 사례는 입원 요청 ID(`SYN-A…`)다. 설계의 "환자-병상 쌍" 사례는 3단계 사가에서 매칭이 생길 때 두 ID를 묶어 만든다.
- 이벤트 ID(멱등 키)는 `<사례 ID>:<이벤트 이름>`이다. 중복은 삽입 전에 걸러 순번에 빈칸이 없게 하고, UNIQUE 제약을 마지막 방어선으로 둔다. UPDATE와 DELETE는 SQLite 트리거로 막는다.
- 합성 데이터를 이벤트로 바꿀 때의 정보 가정(재생 트윈 가정, 운영 지표 해석 시 함께 표기):
  - EV-01: HIS 이벤트는 0~3분 뒤 인지된다.
  - EV-02: 보호자 도착 예정은 당일 08:00~08:30에 병동이 입력한다.
  - EV-03: 보호자 지연이 있으면 원래 예정 30분 전에 예정 변경이 입력되고, 새 예정은 실제 도착을 30분 단위로 올림한 값이다. 실제 도착 시각 자체는 도착 이벤트로만 알 수 있다.
  - EV-04: 입원 요청은 전날 15:00~17:00에 들어온다.
  - EV-05: 청소 요청 이벤트는 기존 방식(병동이 늦게 요청)의 시각이다. 에이전트가 낸 요청은 3단계 이후 별도 이벤트로 기록한다.
- 잡음 주입: 같은 이벤트 ID의 중복 도착, 25~90분 늦은 인지(순서 뒤바뀜), 청소 완료 신호 누락.

## 2026-11-08 3단계 사가: 이벤트 소싱 방식

**맥락**: 설계는 "SQLite 이벤트 기록 또는 LangGraph 체크포인트"를 허용한다.

**결정**
- 사가 상태를 따로 저장하지 않는다. 매 단계 이벤트 저장소를 `as_of=now`로 읽어 접어서(fold) 다시 계산한다. 그래서 프로세스를 강제 종료해도 잃을 상태가 없다.
- 사가가 내는 명령(청소 요청, 미등록 확인, 준비 시각 재계산, 보상 해제, 담당 검토 재분류, 사람 작업)은 `source="saga"` 이벤트로 저장한다. 이벤트 ID는 결정적(`<사례>:saga:<명령>[:<원인>]`)이라 재시작 후 다시 계산돼도 중복 기록되지 않는다(D2).
- 단계는 이벤트 도착 순서가 아니라 관측된 사실의 집합으로 정한다. 그래서 순서가 뒤바뀌어도 같은 상태가 나온다.
- 타이머는 별도 프로세스가 아니라 "기한이 지났는데 사실이 없으면 명령"하는 규칙이다. 명령의 `occurred_at`은 기한 시각, `observed_at`은 실행 시각이다.
- 타이머 기한은 사가 정책값(`SagaPolicy`)이며 생성기 분포를 가져다 쓰지 않는다(평가 순환 방지): 미등록 확인 전날 19:00, 퇴원약 2시간, 청소 지연 일반 120분·종말소독 180분.
- 사가가 내는 청소 요청은 격리 오더가 있으면 종말소독으로 강제한다. 게이트웨이(4단계)가 다시 검사한다.
- 격리 퇴실 병상은 종말소독 완료 신호 없이 빈 병상으로 바꾸지 않는다. 완료 신호가 누락되고 준비 완료만 오면 사람 작업을 만든다.
- 사전 매칭 생성, 환자 연락, 확정은 다른 구성요소(계획 에이전트, 게이트웨이, 원무)가 남기는 이벤트로 받는다. 3단계 테스트는 이 이벤트를 고정 데이터로 넣는다.
- 재매칭 자체(어느 환자를 어느 병상에)는 계획 에이전트(7단계) 몫이다. 사가는 `rematch_requested`만 낸다. 그래서 C04는 7단계 전까지 미구현으로 둔다.
