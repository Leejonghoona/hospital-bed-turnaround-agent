# 설계 결정 기록

설계 문서와 다르게, 또는 설계 문서보다 구체적으로 정해야 할 때 코드보다 먼저 이유를 적는다.

## 2026-11-08 LLM 모델 선정과 배치

**맥락**: 설계 문서는 "운영은 병원 서버의 작은 LLM, 외부 모델 비교는 개발 단계에서 가상 데이터로만"까지만 정해 두었다. 어떤 모델을 어느 역할에 쓰는지, Claude 같은 외부 API를 어디까지 허용하는지는 정해지지 않았다.

**결정** (설계 문서 `#model` 섹션에 표와 근거)
- 역할을 추출 LLM, 계획 에이전트, 질의 응답 셋으로 나누고 역할별로 모델을 고른다. 추출은 추론 모드를 끈 소형 모델, 계획은 추론 모드를 켠 중형 모델.
- 선정 순서: 데이터 위치(관문) → 라이선스(관문) → 한국어 추출 정확도, 도구 호출 유효율, 인젝션 저항, 반복 일관성, 지연과 장비. 3번부터는 재생 평가 하네스로 측정한다.
- 기본값은 결정적 가짜 LLM. 개발 단계에서 `ANTHROPIC_API_KEY`가 있으면 Claude Haiku 5.5(추출), Claude Sonnet 5.5(계획)를 상한 기준선으로 쓴다.
- 운영 1안은 원내 오픈 가중치: 추출 Gemma 4 26B 또는 gpt-oss-20b, 계획 gpt-oss-120b. 장비가 되면 K-EXAONE, 한국어 보강은 Solar Open 100B. 최종 조합은 하네스 결과로 정한다.
- 운영 2안은 Bedrock 서울 단일 리전 Claude(계획만). 추출은 어떤 경우에도 원내 모델이 맡고, 클라우드에는 추출된 코드값과 사례 ID만 보낸다.

**이유**
- Claude 직접 API는 `inference_geo`가 `us`, `global`뿐이고 작업공간 저장 위치는 미국뿐이다(공식 문서, 2026-11 확인). 환자 데이터를 보내면 개인정보보호법 제28조의8 국외 이전과 민감정보 별도 동의 문제가 생기고, 병원 망분리와도 맞지 않는다.
- 하루 퇴원 200건 가정에서 API 비용은 월 약 $44(Haiku 5.5, GPT-6 Luna)~$1,770(Opus 5.5, Gemini 4 Carbon) 수준이라 비용은 결정 요인이 아니다.
- Artificial Analysis 지능 지수 v5.0.1(2026-11-08 조회)은 API 모델만 측정돼 있고(Gemini 4 Carbon 60.0, Opus 5.5 59.1, Sonnet 5.5 54.5, Haiku 5.5 36.5), 원내 후보는 대부분 N/A다. 그래서 원내 후보는 같은 사이트의 IFBench(추출 대리 지표)와 τ²-Bench(계획 대리 지표)로 1차 선별했다: 추출은 Gemma 4 26B 72%, gpt-oss-20b 65%, 계획은 K-EXAONE 74%, gpt-oss-120b 66%.
- EXAONE 4.0은 라이선스가 NC(연구·교육용)라 데모 비교에만 쓴다. K-EXAONE은 병원 서버 규모를 넘는다.

**확인이 더 필요한 것**
- Bedrock 서울 단일 리전 Claude 제공 범위(2차 보도 기준 Opus 5, Sonnet 5)와 가격: AWS 원문 확인.
- Solar Open 100B 가중치 라이선스(Upstage Solar License)의 상업 이용 조건.
- Solar Open2 250B, Solar Open 100B는 Artificial Analysis 측정치가 없음. 하네스로 직접 측정.
- K-EXAONE 라이선스(K Exaone)의 상업 이용 조건.

## 2026-11-08 합성 데이터의 기간과 단계 모델

**맥락**: 설계는 "병동 2개, 병상 24개, 퇴원 30건, 입원 대기 15건"만 정했다. 병상 24개에서 하루에 퇴원 30건은 나올 수 없다.

**결정**
- 퇴원 30건을 평일 5일(하루 6건)에 나눈다. 설계 시연 장면의 "내일 정규 퇴원 6건"과 맞춘다. 같은 날 같은 병상의 퇴원은 1건만 둔다. 다음 퇴원 전까지 그 병상은 대기열 밖 입원(예약 입원, 전동)으로 다시 찬다고 가정하고, 그 입원은 생성하지 않는다.
- 입원 대기 15건은 같은 5일에 나눈다. 배정과 입실 시각은 생성하지 않는다. 그건 계획 에이전트와 도구가 정한다.
- 예외 건수(보호자 지연, 청소 지연, 퇴원 예정 미등록, 입원 취소, 격리 퇴실)는 확률이 아니라 정확한 개수로 넣는다. 회귀 시나리오와 테스트가 항상 같은 수의 예외를 보게 하려는 것이다.
- 단계 소요시간은 로그정규분포로 뽑는다. 파라미터는 중앙값과 P90으로 정의하며, 설계값(가정)이다. 실제 병원 측정치가 아니다.
- 퇴실 전 단계 순서: 퇴원 오더 확정 → 퇴원약과 퇴원 교육을 병행 → 퇴원약 뒤 진료비 심사와 수납 → 보호자 도착 → 퇴실. 퇴실 시각은 수납 완료, 교육 완료, 보호자 도착 중 가장 늦은 시각에 퇴실 준비 시간을 더한 값이다.
- 기존 방식의 청소 요청 지연(퇴실 뒤 병동이 전화하기까지)도 분포로 따로 뽑는다. 에이전트의 "퇴실 즉시 요청"과 비교할 기준선으로 쓴다.

## 2026-11-08 평가 골격을 2단계보다 먼저 만든다

**맥락**: CLAUDE.md 구현 우선순위는 평가 하네스를 5단계에 둔다. 독립 검수(`docs/평가체계_검수.md`)에서 지적이 나왔다. 합격 정의가 구현보다 늦게 나오면 테스트가 구현의 가정을 굳히고, 2단계 이벤트 형식이 미래 정보 누수 검사를 못 하는 모양으로 굳을 수 있다. 사용자가 순서 변경을 승인했다.

**결정**
- 순서를 1 → **1.5 평가 골격** → 2 → 3 → … 로 바꾼다. 1.5에서 만드는 것:
  - 평가표: `docs/평가표.md`
  - 시나리오 라벨 스키마: `src/turnaround/evaluation/scenario.py`
  - 결과 수준 라벨 30개: `evals/scenarios/dev/`
  - 생성기와 별개로 짠 안전 불변 조건 검사기: `src/turnaround/evaluation/invariants.py`
  - 이후 커밋에서 점수판과 에이전트 없음 기준선
  - 나머지 하네스(재생 실행, 모델 비교)는 계속 5단계
- 라벨 30개는 지금 결과 수준(상황, 확인 등급, 필수·금지 행동, 허용 병상)까지만 고정한다. 이벤트 순서와 시각은 2단계 이벤트 형식이 정해진 뒤 채운다.
- 라벨은 Claude가 설계 문서 규칙에서 초안(`status: draft`)을 쓰고, 사용자가 검토해 `approved`로 바꾼다. Claude 계열 모델을 라벨 검수에 쓰지 않는다. 설계 표의 "Opus 5.5 회귀 정답 라벨 검수 보조"는 철회한다.
- 2단계 이벤트 저장소는 이벤트마다 `occurred_at`(발생)과 `observed_at`(인지)을 따로 두고, 미래 정보 누수 테스트(S4)를 합격 조건으로 둔다.
- 비교 기준선은 둘이다: 에이전트 없음, 규칙 모드(LLM 없음). 규칙 모드는 설계 문서에 이미 있는 LLM 장애 경로라 새 범위가 아니다.
- 홀드아웃 봉인 정책: 시드 10000 이후와 분포를 바꾼 설정. 마일스톤에만 만들고 실행한다. AI 에이전트의 홀드아웃 읽기 차단 설정은 사용자 결정 사항이라 적용하지 않았다.

**개입 가정 ID** (운영 지표 O1은 이 ID와 0.5배·2배 민감도를 함께 보고한다)
- AS-01: 에이전트는 퇴실 즉시 청소를 요청한다(기존 요청 지연 → 0분). 결정적 코드가 보장하는 효과.
- AS-02: 대기 정보를 공유하면 수납 대기 기준 초과 건의 수납 시간이 줄어든다. 감소율은 가정값이라 정해지기 전까지 0으로 둔다.
- AS-03: 사전 매칭이 있으면 병상 준비 완료부터 병동 문의까지 지연이 사라진다. 병동 회신 지연은 합성 응답자 분포를 따른다(G11, 2단계 이후 정의).
- AS-04: 보호자 도착 예정 갱신을 반영하면 준비 시각 재추정이 갱신 시점에 일어난다. 실제 도착은 바뀌지 않는다.

## 2026-11-08 2단계 이벤트 저장소의 시간 의미론과 사례 ID

**결정**
- 이벤트마다 `occurred_at`(현실에서 일어난 시각)과 `observed_at`(시스템이 알게 된 시각)을 둔다. `observed_at < occurred_at`은 거부한다. 조회의 `as_of`는 `observed_at` 기준이다. 판단 시점보다 늦게 인지된 이벤트는 보이지 않는다(평가표 S4).
- 사례 ID는 지금 퇴원 사례는 퇴원 ID(`SYN-D…`), 입원 대기 사례는 입원 요청 ID(`SYN-A…`)다. 설계의 "환자-병상 쌍" 사례는 3단계 사가에서 매칭이 생길 때 두 ID를 묶어 만든다.
- 이벤트 ID(멱등 키)는 `<사례 ID>:<이벤트 이름>`이다. 중복은 삽입 전에 걸러 순번에 빈칸이 없게 하고, UNIQUE 제약을 마지막 방어선으로 둔다. UPDATE와 DELETE는 SQLite 트리거로 막는다.
- 합성 데이터를 이벤트로 바꿀 때의 정보 가정(재생 트윈 가정, 운영 지표 해석 시 함께 표기):
  - EV-01: HIS 이벤트는 0~3분 뒤 인지된다.
  - EV-02: 보호자 도착 예정은 당일 08:00~08:30에 병동이 입력한다.
  - EV-03: 보호자 지연이 있으면 원래 예정 30분 전에 예정 변경이 입력되고, 새 예정은 실제 도착을 30분 단위로 올림한 값이다. 실제 도착 시각 자체는 도착 이벤트로만 알 수 있다.
  - EV-04: 입원 요청은 전날 15:00~17:00에 들어온다.
  - EV-05: 청소 요청 이벤트는 기존 방식(병동이 늦게 요청)의 시각이다. 에이전트가 낸 요청은 3단계 이후 별도 이벤트로 기록한다.
- 잡음 주입: 같은 이벤트 ID의 중복 도착, 25~90분 늦은 인지(순서 뒤바뀜), 청소 완료 신호 누락.

## 2026-11-08 3단계 사가: 이벤트 소싱 방식

**맥락**: 설계는 "SQLite 이벤트 기록 또는 LangGraph 체크포인트"를 허용한다.

**결정**
- 사가 상태를 따로 저장하지 않는다. 매 단계 이벤트 저장소를 `as_of=now`로 읽어 접어서(fold) 다시 계산한다. 그래서 프로세스를 강제 종료해도 잃을 상태가 없다.
- 사가가 내는 명령(청소 요청, 미등록 확인, 준비 시각 재계산, 보상 해제, 담당 검토 재분류, 사람 작업)은 `source="saga"` 이벤트로 저장한다. 이벤트 ID는 결정적(`<사례>:saga:<명령>[:<원인>]`)이라 재시작 후 다시 계산돼도 중복 기록되지 않는다(D2).
- 단계는 이벤트 도착 순서가 아니라 관측된 사실의 집합으로 정한다. 그래서 순서가 뒤바뀌어도 같은 상태가 나온다.
- 타이머는 별도 프로세스가 아니라 "기한이 지났는데 사실이 없으면 명령"하는 규칙이다. 명령의 `occurred_at`은 기한 시각, `observed_at`은 실행 시각이다.
- 타이머 기한은 사가 정책값(`SagaPolicy`)이며 생성기 분포를 가져다 쓰지 않는다(평가 순환 방지): 미등록 확인 전날 19:00, 퇴원약 2시간, 청소 지연 일반 120분·종말소독 180분.
- 사가가 내는 청소 요청은 격리 오더가 있으면 종말소독으로 강제한다. 게이트웨이(4단계)가 다시 검사한다.
- 격리 퇴실 병상은 종말소독 완료 신호 없이 빈 병상으로 바꾸지 않는다. 완료 신호가 누락되고 준비 완료만 오면 사람 작업을 만든다.
- 사전 매칭 생성, 환자 연락, 확정은 다른 구성요소(계획 에이전트, 게이트웨이, 원무)가 남기는 이벤트로 받는다. 3단계 테스트는 이 이벤트를 고정 데이터로 넣는다.
- 재매칭 자체(어느 환자를 어느 병상에)는 계획 에이전트(7단계) 몫이다. 사가는 `rematch_requested`만 낸다. 그래서 C04는 7단계 전까지 미구현으로 둔다.

## 2026-11-08 라벨 토론 합의: 설계 공백을 메우는 라벨 전제 (사용자 승인 대기)

**맥락**: 사용자 요청으로 라벨 30개를 다중 에이전트 토론으로 다시 검토했다(`docs/라벨_토론_결과.md`, 원문 `docs/라벨토론/`). 1라운드에서 토론자 셋(병상관리 실무, 감염관리·환자안전, 평가 설계)이 상황만 보고 블라인드로 도출했다. 2라운드에서 서로의 결과와 초안을 비교해 양보하거나 반박했다. 아래는 설계 문서가 침묵하거나 모호해서 라벨이 갈리던 지점의 합의다. 라벨과 함께 사용자 승인으로 확정한다. 토론자가 모두 Claude 계열이라는 한계가 있다(같은 계열 편향, G13).

**합의 (셋 모두 동의)**
- LP-01 격리 병실: 공기감염 격리는 음압격리실만, 접촉 격리는 음압격리실 또는 1인실이다. 개념 계층(하위 개념 제약)이 규칙 표의 "음압실 또는 1인실"보다 우선한다.
- LP-02 동명이인: 같은 병실이면 배정 기준 위반(SHACL 차단), 같은 병동의 다른 병실이면 담당 검토, 다른 병동이면 검토 사유가 아니다.
- LP-03 종말소독 강제: 게이트웨이는 거부하지 않고 값을 고쳐 실행한다. 고친 사실은 감사 기록(`overridden_from`)으로 남긴다. 거부하면 퇴실 즉시 요청(AS-01)이 깨지고 K 상태 병실이 방치된다.
- LP-04 소독 전 확정 거부: 정보 변경(G1)이 아니라 선행 조건 미충족이다. 재분류하지 않고 보류하며, 종말소독 완료 신호 뒤 재검토 없이 다시 확정할 수 있다.
- LP-05 사람 개입 세는 법: 담당 확인·검토 1, 병동 회신 1, 원무 확정 1, 사람 작업 1. 1단계에서 병동 확인과 담당 검토가 같은 3회인 것은 설계 구조다. 등급은 감사 로그의 등급 값과 검토 카드(H2)로 채점하고, H1은 단계별 부담 보고에만 쓴다.
- LP-06 상황 보강 원칙: 사실(어느 병상이 비었나, 무엇이 바뀌었나)은 상황에 보강한다. 규칙(소아 병실 제약 등)이 필요한 곳은 보강하지 않고 등급과 순서만 채점한다(D01, D02, F02).
- LP-07 시나리오 수: 30개를 나누지 않는다(C1 분모 고정). 단계가 섞인 시나리오는 행동별 `stage`와 `level`로 부분 채점하고, 주입판·짝 시나리오·2막은 30개에 세지 않는 하위 고정 데이터로 둔다.
- LP-08 질의의 부재 답변: 레코드가 없을 때는 `answer_no_record`로 답한다. 권한 거부(`refuse_query`)와 섞으면 I2가 오염된다.
- LP-09 상태 재구성 시점: 사례 상태는 관측된 사실의 집합으로 재구성하고(순서 무관), 판단에 쓸 수 있는 정보는 `observed_at` 기준이다.

## 2026-11-08 LP-01 개정: 전파경로 주의 체계 (사용자 결정 A안)

- LP-16 전파경로 주의는 집합이다. 접촉, 비말, 공기 중 여러 개를 가질 수 있다(예: 수두는 공기+접촉). 병원체(코호트 키)와 상태(확진, 의심, 선제 격리)를 함께 둔다. 기존 `isolation_type`은 가장 엄격한 주의 하나를 뜻하는 호환 필드로 남긴다(공기 > 비말 > 접촉).

  - 공기주의는 음압격리실만 쓴다. 활동성 폐결핵 환자는 방을 함께 쓰지 않는다.

  - 선행 조건: 격리 퇴실 병상의 종말소독 완료 신호(LP-04)

  - 정책 버전, 자율화 단계, 승격 유형
  - 소아 연령 기준, 1·2순위 점수 차 기준

- 조회 권한: 역할별 허용 필드만 답한다. 환경 업체는 병상 번호, 예상 시각, 청소 유형만 받는다.
- 병동 통지: 수용 회신까지 받은 매칭이 확정 직전에 거부되면 병동에 철회 통지를 보낸다(사용자 결정).
- 사가 보강(4단계 라벨 대응): 보호자 예정 변경 시 지연 사유 코드(보호자) 기록, 수납 대기 기준 초과(퇴원약 준비 뒤 정책값 60분) 시 원무 화면 대기 정보 공유와 지연 사유(수납) 기록. 정책값은 설계 가정이다.

**관리자 직접 수정 (사용자 질문으로 추가, 설계 공백이었다)**
- 맥락: VIP, 환자·보호자 특수 요청, 임상 사유로 병상관리 담당이 에이전트 배치를 직접 바꿔야 할 수 있다. 원래 설계에는 원무 확정과 담당 검토만 있고, 확정 뒤 사람이 직접 바꾸는 경로가 없었다.
- 결정:
  - 직접 수정은 게이트웨이의 별도 경로(`manual_override`)로만 받는다. 허용 역할은 병상관리 담당이다.
  - 사유 코드는 필수다: vip, patient_request, clinical, operational, other.
  - 안전 규칙(SHACL 위반)은 사람도 그냥 넘을 수 없다. 감염관리실의 예외 승인이 있을 때만 적용하고, 그 사실을 감사 로그에 남긴다.
  - 점수 규칙(진료과 선호, 음압실 보존)은 사람 판단이 이긴다.
  - 적용하면 그 사례를 "사람 고정"으로 표시한다. 이후 에이전트의 재매칭 제안은 게이트웨이가 거부한다(사람 결정을 에이전트가 되돌리지 않는다). 기존 매칭은 해제하고, 수용 회신이 있었으면 병동에 통지한다.
  - VIP 같은 사유 코드는 감사 로그와 병상관리 화면에만 남긴다. 조회 권한 규칙에 따라 환경 업체 등에는 내보내지 않는다.
  - 직접 수정은 설계의 개선 루프(기록 → 분석 → 검증 → 반영)의 입력이 된다. 에이전트 배치를 사람이 바꾼 비율은 사후 수정률 지표가 된다.

## 2026-11-08 라벨 수정: B02 거부 사유 명시 (민감도 검사 결과)

- 시나리오 민감도 검사(G4)에서 "판단 정보 재확인"을 꺼도 B02가 통과했다. 퇴원이 취소되면 병상이 계속 사용 중이라 게이트웨이가 "병상 사용 중"으로 거부했고, 라벨이 거부 사유를 요구하지 않았다.
- B02의 목적은 제안 시점 판단 정보 재확인(G1)이다. `reject_at_proposal`에 `reason: info_changed`를 추가한다. 승인된 라벨의 수정이라 여기에 먼저 적는다.
- 같은 검사에서 "병동 수용 회신 확인"은 회귀 30개 중 어느 것도 잡지 못했다(모두 회신 뒤 확정). 게이트웨이 단위 테스트는 잡는다. 다음 홀드아웃 세트 후보로 둔다: 수용 회신 없이 원무가 확정을 누르는 경우.

## 2026-11-08 스펙 v1.0 동결: 현실 조사 반영 (LP-23~LP-28)

근거: `docs/검토/스펙현실검증.md`. 아래 인용은 작업자가 원문을 직접 열어 확인했다(질병관리청 「의료관련감염 표준예방지침」 2017, 제3자 사본. 공식본 대조는 남은 과제).

- **LP-23 (LP-20 정정) 환기 대기는 표에서 찾는다.** 지침은 "공기주의 입원 환자 병실은 청소를 하고 적절한 환기 후에 사용한다(시간당 공기교환 횟수 4회 기준 2시간 정도 또는 기관의 공조시스템에 따라 조정)"라고 한다. 비말주의는 "에어로졸이 없어질 때까지 충분한 시간이 지난 후" 청소한다(5.4.5.1). 제5장 부록 3에는 시간당 공기순환 횟수별 에어로졸 제거 시간표(PHAC 2012)가 있다.
  - 앞서 쓴 "지침에 수치 없음, 30분"은 틀렸다. 이전 조사가 부록 3을 놓쳤고, 작업자가 확인하지 않았다.
  - 결정: 병실마다 시간당 공기순환 횟수를 두고, 대기 시간은 부록 3 표의 99.9% 제거 열에서 찾는다. 예: 12회 35분, 6회 69분, 4회 104분. 순환 횟수 기본값(음압실 12회, 일반실 4회)과 제거율은 정책값이며 설계 가정이다.
- **LP-24 (LP-17·GW-10 개정) 안전 규칙 예외는 3단계로 나눈다.**
  - 금지(예외 경로 없음): 활동성 폐결핵 방 공유. 근거: "활동성 폐결핵은 … 방을 공유하지 않는다 (IB)", 5.5.2.4.
  - 감염관리 전문가 사전 승인:
    - 공기주의 환자의 일반 병실 배치(5.5.2.6 "감염관리 전문가와 상의한다")
    - CRE 환자의 다인실 배치(5.2.1 "격리실의 우선 순위는 … 감염관리실무자가 결정한다. 단, 카바페넴내성장내세균이 분리되는 경우에는 가장 우선적으로 가능한 한 1인실")
    - 접촉주의 코호트에 고위험 환자(5.3.2.3)
    - 야간·주말 승인 대행 역할은 정책 파일에 둔다. 대행 체계의 원문은 찾지 못해 설계 가정이다.
  - 사유 입력 후 진행, 사후 검토: 위에 해당하지 않는 배정 규칙 예외(가족 동반으로 인한 성별 병실 예외 등). 근거를 찾지 못한 설계 선택이다. 사후 검토 기한은 "24시간"이 아니라 운영 달력의 "다음 근무일 정오"다.
  - 화면 용어는 "브레이크 글래스"가 아니라 "사유 입력 후 진행"이다.
  - 동명이인은 예외 승인 대상이 아니다. 같은 병실은 계속 금지하고, 같은 병동은 담당 검토와 동명이인 구분 표시로 처리한다(EMR 인증 기준 F004 "동명이인 구분자 표시").
- **LP-25 병상 배정 역할과 시간대.** 공개 사례에서 배정은 원무 입원 파트의 일이다(길병원 "센터별 입원 원무 담당자", 서울아산 배정 담당 직원). 서울대병원 입원 창구 운영 시간은 평일 09–18시이고 그 밖에는 응급실 수납창구다.
  - 결정: "병상관리 담당"은 시간대별 역할 매핑(정책 파일)으로 바꾼다. 주간 입원 원무, 야간·휴일 당직 원무 또는 응급실 수납이다. 야간 배정 주체는 원문을 찾지 못해 설계 가정이다.
  - 인계와 마감 기한은 운영 달력 기준이다.
- **LP-26 다제내성균 동실자 감시 대기 동결.** 지침 8.3.4는 다제내성균 환자와 같은 병실 환자에게 "능동감시 결과가 나올 때까지 코호트 격리하고 병실 이동을 제한"하라고 한다. 병실 사용 중지 이벤트에 `surveillance_hold` 사유를 둔다. 신규 입실과 재원 환자 이동을 함께 막는다. 병동 폐쇄 결재선과 음압실 점검 주기는 원문을 찾지 못해 설계 가정이다.
- **LP-27 퇴원약 단계.** 세브란스 안내 "퇴원 당일 퇴원처방, 퇴원약 조제 … 절차가 완료되면". 서울성모 퇴원처방 수정률은 월 15–16%이고, 수정 사유 1위는 퇴원 보류다(데일리팜, 2차).
  - 결정: 퇴원약을 처방 발행 → 조제 → 병동 도착 → 처방 수정으로 나눈다. 지연 타이머의 기준점은 처방 발행 시각이다. 합성 수정 비율은 15%(합성 가정)다.
- **LP-28 사망 퇴원과 임종실.** 2024년 8월부터 300병상 이상 종합병원에 임종실 설치가 의무다(메디게이트 뉴스, 보건복지부 의료법 시행규칙 개정 인용, 2차). 임종 환자가 임종실로 옮기면 원래 병상은 그때 빈다.
  - 결정: "임종실 전실" 경로를 둔다. 사망 퇴원에서는 보호자·수납 지연 경보를 억제하고, 사망 정보를 외부에 내보내지 않는다. 사망 후 병실 소독이 일반 퇴원과 어떻게 다른지는 근거가 없어 일반 규칙(격리 여부)을 따른다.
- 직접 수정 태그(GW-11)는 업계 관행이라는 근거가 없다. "설계 선택"으로 쓴다.
- 조사 에이전트가 "세종병원 기사를 다시 찾지 못함"이라고 했으나, 작업자가 앞서 원문을 직접 받아 확인했다(라포르시안 idxno=240998).
- 현직자 인터뷰로 보완할 항목: 야간 배정 주체, 감염관리 야간 승인 체계, 병동 폐쇄 결재선, 음압실 점검 주기, 주말 약제부 운영, HIS 퇴원 취소·재결정 화면.

## 2026-11-08 규칙의 출처 계층: 지침(FM)과 병원 규칙, 현장 운영 (LP-29)

**맥락**: 사용자 우려. 문서화된 지침과 실제 병원 운영은 다를 수 있다(예: 환기 시간을 병원 규칙으로 단축). 시범 조사(`docs/검토/현장실태_시범.md`) 결과 공개 자료로는 "부분 가능"하다. 작업자가 원문으로 확인한 내용은 다음과 같다.
- 지침 자체가 병원 조정을 허용한다: "2시간 정도 **또는 기관의 공조시스템에 따라 조정**". 병원 값이 지침과 달라도 위반이 아닐 수 있다.
- 실태는 지침과 다르다: 퇴원병실을 소독제로 닦는 기관 87.4%(191개 기관 설문, 2022), 일반병동 1인실 격리 시행 19.5%(41개 병원, AJIC 2017), 병동 외기 간헐 도입 53%(21개 기관, 2018).
- 특정 병원의 실제 값(퇴실 후 대기 몇 분, 청소 소요, 실측 환기 횟수)은 내부 규정이라 공개 자료로 알 수 없다. 인터뷰, 설문, 병원 운영 데이터가 필요하다.

**결정**
- **POL-1 규칙 값마다 출처 계층을 단다.** 법령 > 정부 지침 > 병원 규칙 > 현장 관행 > 설계 가정 순서이고, 근거 인용을 함께 둔다. 정책 파일의 값은 출처 등급과 근거를 가진다.
- **POL-2 병원 규칙은 지침과 달라도 된다. 단 차이를 숨기지 않는다.**
  - 지침이 조정을 허용하는 값(환기 시간 등)은 병원 값이 우선한다. 지침 기본값과 다르면 "지침 대비 단축/연장" 표시를 화면과 감사 기록에 남긴다.
  - 법령 값과 지침의 금지 조항(예: 활동성 폐결핵 방 공유 금지)은 병원 규칙으로 바꿀 수 없다.
- **POL-3 (2단계 온보딩) 문서상 규칙과 실제 운영의 차이를 데이터에서 찾는다.** 병원 이벤트 기록에서 실제 간격(퇴실 → 청소 시작 등)을 추정한다. 정책 파일 값과 크게 다르면 "문서상 120분, 실제 운영 중앙값 40분"처럼 사람에게 보여 주고 결정을 받는다. 시스템이 어느 쪽이 맞다고 정하지 않는다.
- 이 설계는 엔드픽처의 "어느 병원이든 그 병원에 맞게"의 핵심이다. FM 기본값으로 시작하고, 병원 규칙으로 덮어쓰고, 실제 운영과의 차이는 드러낸다.

## 2026-11-08 MVP 가정 목록 (MVP 뒤 검토)

사용자 지시("내 결정이 필요한 건 MVP가 나온 뒤에 수정")에 따라, 결정이 필요한 지점은 아래처럼 가정을 두고 진행한다. MVP가 나오면 이 목록을 함께 검토한다.

- **MA-01 (GW-10) 야간·휴일 사전 승인 대행 = 감염내과 당직(`id_oncall`).** 표준예방지침은 "감염관리 전문가와 상의"까지만 정한다. 야간 대행 역할은 병원마다 다르다(설계 가정). 정책 파일 `safety_exception_roles`에서 바꾼다.
- **MA-02 (GW-10) 사후 검토 기한 = 다음 평일 정오, 공휴일 미반영.** 운영 달력(SAG-8)이 들어오면 공휴일을 반영한다.
- **MA-03 (GW-10) 위반 코드별 단계 분류.** 금지: 결핵 방 공유(지침 5.5.2.4), 같은 병실 동명이인, 성별 누락, 없는 병상. 사전 승인: 공기주의 일반실(5.5.2.6), CRE/CPE 다인실(5.2.1), 코호트 병실의 비코호트·보호격리·선제격리(5.3.2.3). 사유 입력: 그 밖의 격리 병실 규칙(5.3.2.4·5.4.2.5 차선책), 성별 병실. 분류 안 된 위반은 금지로 본다. 동명이인 금지와 성별 병실 사유 입력은 설계 가정이다.
- **MA-04 (GW-10) 사유 입력 단계에서 사전 승인자가 함께 승인하면 사후 검토 작업을 만들지 않는다.** 이미 전문가가 본 건이기 때문이다.

- **MA-07 (SAG-2a, DAT-9) 환기 대기 = 병실 공기순환 횟수로 지침 부록 3 표(99.9% 제거 열)에서 찾는다.** 표에 없는 횟수는 같은 식(ln 1000 / 횟수 × 60분)을 올림해 보수적으로 쓴다. 표 9개 값 중 작업자가 원문에서 직접 확인한 값은 12회 35분, 6회 69분, 4회 104분이고, 나머지는 같은 식으로 계산한 값과 일치한다(PHAC·CDC 표와 같은 출처). 비말주의도 같은 표를 쓴다. 지침 5.4.5.1이 "에어로졸이 없어질 때까지"라고만 해서, 공기주의 표를 빌려 쓰는 것은 설계 가정이다.

- **MA-08 (POL-1) 정책 파일 `provenance`에 값마다 출처 등급과 근거를 단다.** `pediatric_age`처럼 근거를 찾지 못한 값은 `design_assumption`으로 둔다.
- **MA-09 (POL-2) 병원 규칙(`ventilation.hospital_wait_min`)이 지침 값과 다르면 청소 요청 이벤트에 `guideline_delta`(예: "지침 대비 44분 단축")를 싣는다.** 이벤트 저장소가 감사 기록이므로 화면도 이 값을 읽는다. 지침 금지 조항(결핵 방 공유 금지)은 정책 파일에서 바꾸면 불러오기 단계에서 거부한다.
- **MA-10 (DAT-7, SAG-6) 퇴원약 단계.** 처방 발행(`DISCHARGE_RX_ISSUED`) → 수정(`DISCHARGE_RX_REVISED`, 사유) → 조제(`DISCHARGE_RX_DISPENSED`) → 병동 도착(`MEDICATION_READY`).
  - 지연 타이머 기준점은 처방 발행 시각이다. 처방 이벤트를 보내지 않는 원천이면 오더 확정 시각으로 대신한다(하위 호환).

  - 합성 단계 시각(발행 = 오더 후 0~30분, 수정 = 발행 후 15~60분, 재조제 30~60분, 조제 → 병동 도착 10~25분)은 설계 가정이다. 수정 비율은 15%(LP-27). 퇴원약 단계는 별도 난수열을 써서 기존 합성 데이터의 다른 값은 바뀌지 않는다.
  - 테스트 정정: 미등록 감지 테스트가 "실제 등록 시각"으로 오경보를 판정해 관측 지연(0~3분)에 취약했다. 사가와 같은 "인지 시각" 기준으로 고쳤다.
- **MA-11 (SAG-8) 사람 작업 목록은 사가와 같은 방식(이벤트 접기, 결정적 ID, 재시작 멱등)의 별도 실행기 `WorklistRunner`가 맡는다.** 운영 달력과 역할 매핑은 `config/operations.yaml`에 둔다.
  - 간호 3교대 07/15/23시, 입원 창구 평일 09–18시(서울대병원 안내, LP-25). 창구 밖 시간의 배정 담당은 당직 원무(`night_admin`), 감염관리는 감염내과 당직(`id_oncall`)이다. 둘 다 설계 가정이다.
  - 교대 시각에 열린 작업은 다음 근무조 담당에게 인계 이벤트를 남긴다. 마감(작업 종류별 분, 또는 작업의 `due`)을 넘기면 상위 담당(수간호사·야간 감독 `nursing_supervisor`, 원무 책임 `admission_lead`, 감염관리 책임 `ipc_lead`)에게 한 번 올린다. 마감 분과 상위 담당은 설계 가정이다.
  - 담당 검토 큐(`CASE_ROUTED_REVIEW`)도 작업으로 본다. 같은 사례에 승인, 확정, 직접 수정, 입원 취소가 생기면 닫힌다.
  - 합성 병원의 휴무일 목록은 비운다. 합성 기간 첫날 2026-03-02은 실제 달력으로는 삼일절 대체공휴일이지만, 합성 데이터에서는 평일로 본다(설계 가정). 실제 병원은 휴무일을 넣는다. 게이트웨이의 사후 검토 기한(MA-02)도 이 달력을 쓴다.
- **MA-12 (DAT-8) 근무 인원표는 `StaffingSource` 인터페이스와 합성 표(병동 12병상 기준 주간 3, 초번 3, 야간 2명, 근무조 10% 결원 1명)로 둔다.** 인원은 설계 가정이며, 배정 점수에서 쓸지는 7단계 에이전트 도구에서 정한다.
- **MA-13 (SAG-9, DAT-10) 사망 퇴원은 `END_OF_LIFE_ROOM_TRANSFER`(임종실 전실) 이벤트로 받는다.** 퇴원 결정 없이 와도 사례를 만들고, 그 시각을 병상이 빈 시각으로 본다(청소 요청 즉시). 퇴실 전 경보(등록 확인, 퇴원약 지연, 처방 없음, 보호자 지연, 수납 대기)는 모두 억제한다. 사가 명령과 청소 요청에는 사망 여부를 싣지 않는다. 조회 허용 필드에도 없다.
  - 자의 퇴원(`discharge_type: ama`)은 처방 없음 알림만 억제한다. 처방 없이 나갈 수 있기 때문이다(설계 가정). 그 밖의 흐름은 일반 퇴원과 같다.
  - 합성 데이터에는 병원마다 사망 1건, 자의 퇴원 1건을 둔다(격리·미등록·보호자 지연 건이 아닌 퇴원에서 고름. 합성 가정). 사망 후 병실 소독은 일반 규칙(격리 여부)을 따른다(LP-28).

## 2026-11-08 7단계 계획 에이전트 구현 (AGT-1~7)

- **AGT-1 LLM 인터페이스**: `complete_json(task, system, user) -> dict` 하나. 기본은 결정적 가짜 LLM이다. 실제 모델은 `TURNAROUND_LLM`, `TURNAROUND_LLM_MODEL`, 키, 그리고 `TURNAROUND_EXTERNAL_LLM_ACK=synthetic-only`가 모두 있을 때만 붙는다. 마지막 값은 "외부 API에는 합성 데이터만 보낸다"는 확인이다(운영 정책 `external_llm: deny`는 그대로). SDK 대신 HTTP 호출(requests)로 붙여 의존성을 늘리지 않았다.
- **AGT-2 도구가 안전을 보장한다.** 후보 필터는 게이트웨이와 같은 SHACL 검사를 쓴다. 배정 기준이 모두 병실 단위라 병실마다 한 번만 검사한다(같은 병실 빈 병상의 판정이 같음을 테스트로 확인). 게이트웨이가 제안 시점과 확정 직전에 다시 검사하므로 이중 방어다.
- **점수 = 목표 함수 4~5항**(정책 파일 `scoring`, 설계 가정): 진료과 병동 일치 +30, 공기주의가 아닌 환자의 음압실 −40(LP-18), 1인실 희망 +20, 사유 없는 1인실 −15, 고위험 환자 간호사실 근처 +10, 병동 진행 중 제안 1건당 −3, 준비까지 10분당 −1.
- **재매칭 기준(6항)**: 이득 3점(준비 30분 단축에 해당) 이상일 때만. 처음 15점으로 두었다가, 청소 지연 기준(120분)을 넘긴 경우에도 남은 대기가 45~70분이라 이득이 4.5~7점에 그쳐 재매칭이 일어나지 않았다. 정책 파일에서 바꾼다.
- **대안 2개는 다른 병실에서** 고른다. 같은 병실의 같은 조건 병상은 대안이 아니다. 같은 병실 병상을 대안으로 넣으면 점수 차가 0이라 모든 사례가 "점수 근접" 검토로 갔다.
- **AGT-3 선택과 대체**: LLM은 도구가 거른 상위 5개 후보 중 하나를 고르고 설명을 쓴다. 장애, 형식 오류, 후보 밖 선택이면 규칙 모드(도구 1순위)로 내려가고 기록을 남긴다(NFR-4). 가짜 LLM은 점수 1순위를 고르므로 규칙 모드와 같은 선택을 한다. 차이는 실제 모델 비교(EVL-4)에서 본다.
- **SEC-3**: 계획 에이전트 입력은 구조화 필드뿐이다. 전달사항·메모 원문은 추출기만 읽고, 허용 필드(보호자 도착 시각, 보조기구, 1인실 희망 언급) 밖의 출력은 버린다. F01·F02 실행기가 에이전트 입력에 원문이 없는지 구조 검사를 한다.
- **AGT-6 질의 응답**: LLM은 질문을 조회 의도로 바꾸는 일만 한다. 답의 사실은 조회 도구가 레코드에서 가져오고, 근거 레코드 ID가 없으면 "레코드 없음"으로 답한다. 합성 일정(Appointment) 레코드를 둔다.
- **실행기**: 시나리오 상황의 "빈 병상"만 비우고 나머지를 재원 환자로 채운다. 사람 응답(담당 승인 5분, 병동 회신 10분, 확정 15분 뒤)은 실행기가 흉내 낸다. 주입판 제안(게이트웨이 방어 시험)은 별도 저장소에서 돌리고 에이전트 제안으로 채점하지 않는다.
- **게이트웨이 보강**: 병상 없음 제안에 입력 누락 사유가 있으면 데이터 수정 작업을 만든다(D04). 재매칭으로 다른 병상을 확정하면 이전 사전 매칭을 푼다(E02).

## 2026-11-08 FHIR R4 입력 어댑터 (EVT-7, 검토: `docs/검토/FHIR_테크리드.md`)

**왜 FHIR를 정본으로 하지 않았나.** FHIR 리소스는 상태 스냅숏이고, 이 시스템은 이벤트 의미(현실 시각과 인지 시각의 분리, 중복 도착, 완료 신호 누락)에 기댄다. 현재 상태 번들만 받으면 중간 상태와 인지 시각이 사라져 미래 정보 누수 검사(S4)가 무의미해진다. FHIR `Location.physicalType`에는 음압격리실 개념도 없다. 그래서 내부 이벤트 모델을 정본으로 두고, FHIR는 경계 어댑터로만 붙인다(부패 방지 계층). 사가·게이트웨이·평가기는 FHIR를 모른다.

**범위**: 내보내기(내부 이벤트 → R4 `Bundle.type=history`), 들여오기(번들 → 내부 이벤트), 이중 실행 동등성 검증. **비목표**: FHIR 서버, 구독, 실제 HIS 쓰기 연동(설계 "제외"), KR Core 프로파일 검증(Java 검증기 필요), SNOMED CT 전면 정렬. R4 기본 구조 검증은 `fhir.resources`(R4B 모듈, R4와 이 리소스들의 구조가 같음)를 테스트 의존성으로만 쓴다.

**대응표**
| 내부 | FHIR R4 | 비고 |
|---|---|---|
| 병동·병실·병상 | `Location` (physicalType `wa`·`ro`·`bd`, `partOf`) | 음압실, 병실 성별, 코호트 키, 공기순환 횟수는 확장(extension). 표준 개념이 없다 |
| 환자 기본 정보 | `Patient` (gender, birthDate는 나이에서 역산하지 않고 확장으로 나이) | 합성 가명 |
| 전파경로 주의 | `Flag` + SNOMED CT 409524006(공기)·409525007(비말)·409529001(접촉) | 병원체 코호트 키·확진 여부는 확장 |
| 이벤트 1건 | `Task` 1개 (code = 내부 이벤트 종류, CodeSystem `urn:turnaround:event-type`) | 상태 스냅숏이 아니라 사건 기록으로 쓴다 |
| `occurred_at` | `Task.executionPeriod.start` (= `authoredOn`) | 현실 시각 |
| `observed_at` | `Bundle.entry.resource.meta.lastUpdated` | 인지 시각. 순서는 번들 항목 순서가 정본 |
| `event_id` | `Task.identifier` (system `urn:turnaround:event-id`) | 멱등 키 |
| `case_id` | `Task.groupIdentifier` | 사례 ID |
| `source` | `Task.requester.display` | his, human, saga 등 |
| `payload` | `Task.input[]` (type.text = 키, value[x]) | 목록·사전은 JSON 문자열. 환자 필드는 `Task.for` → Patient·Flag에서 다시 만든다 |

**검증 기준(합격선)**: 시드 0~199에서 "생성기 → 이벤트"와 "생성기 → 이벤트 → FHIR → 어댑터 → 이벤트"의 이벤트 스트림이 같다(사전 비교와 해시). 점수판 지표와 회귀 시나리오 결과는 이벤트가 같으면 같다. 잡음 주입은 어댑터 뒤(이벤트 단계)에 둔다.

## 2026-11-08 8단계 몬테카를로 가용 병상 추정

- **추정 대상**: 병동·일마다 "그날 퇴원 병상 중 기준 시각까지 준비 완료되는 병상 수". 추정 시점(09:00)까지 인지한 이벤트만 쓴다(as_of 조회). 이미 일어난 단계는 그 시각을, 남은 단계만 분포에서 2000번 뽑는다.
- **기준선**: 약한 기준선은 설계 문서대로 "퇴원 확정 병상은 모두 빈다". 강한 기준선은 단계마다 중앙값을 넣은 결정적 추정이다.
- **MA-14 (MVP 가정) 기준 시각을 정오와 15:00 두 개로 본다.** 합성 기존 방식에서는 정오까지 준비 완료되는 병상이 0.6%뿐이다(준비 완료 중앙값 15:00). 그래서 정오 추정은 "0개"로 자명해진다(MAE 0.015, 강한 기준선과 같음). 설계는 정오를 그대로 두고, 의미 있는 비교는 오후 입원 시각인 15:00에서 한다. 15:00이 "오후 입원 기준 시각"이라는 근거는 찾지 못했다(설계 가정).
- **포함률이 목표(70~90%)보다 높다(92~95%).** 병상 수는 정수라 P10과 P90 경계에 같은 값이 몰려 구간이 보수적으로 넓어진다. 고치지 않고 그대로 보고한다.
- 과정 모형(보호자 지연 확률 0.2, 청소 지연 확률 0.13, 도착 예정이 없으면 11:00)은 과거 데이터에서 맞춘 값이라고 가정한다. 합성 데이터에서는 생성기 설정에서 가져왔다. 생성기와 같은 구조의 과정 모형이라 dev 결과는 낙관적이다. 그래서 분포 이동 홀드아웃(실제만 P90 +30%, 또는 보호자 지연 6 → 10건)으로 따로 잰다.

## 2026-11-08 모델 성능점검 중 찾은 결함 (하네스가 잡은 것)

- **계획 에이전트 프롬프트에 "json" 단어가 없어 OpenAI JSON 모드가 모든 호출을 거부했다(HTTP 400).** 에이전트는 매번 규칙 모드로 내려갔고, 회귀 시나리오는 대체 경로 덕분에 그대로 통과했다. 통과율만 봤다면 놓쳤다. 도구 호출 유효율(P1) 0.0이 이를 드러냈다. 프롬프트를 고쳤고, 대체 경로가 결과를 가리는 문제는 점검표에 "P1은 통과율과 따로 본다"로 적는다.
- **질의 해석에서 실제 모델이 인자를 `parameters` 아래에 넣고 값을 한국어("내일", "오전")로 냈다.** 프롬프트에 정확한 형식을 넣고, 코드에서 결정적으로 정규화한다(사실을 바꾸지 않는 형식 보정).
- **OpenAI 기본 온도(1)에서는 인젝션 짝 비교(I1)가 무작위성과 섞인다.** 온도를 받는 모델은 0으로 두고, 같은 입력을 두 번 돌린 차이(무작위성 바닥값)를 함께 보고한다. 추론 모델(gpt-5 계열)은 온도 설정을 받지 않아 바닥값이 0이 아닐 수 있다.
- **불리언 필드의 false는 "언급 없음"과 같게 본다.** 소형 원내 모델은 언급 없는 필드에 false를 채우는 경향이 있다. 쓰는 쪽에서 차이가 없어 정규화한다.

## 2026-11-09 라벨 재작성과 측정 계획 결정 (사용자 "추천대로")

- **U3 도착 시각 날짜**: 상대 날짜로 뽑는다(`day_offset` + `HH:MM`). 날짜 계산은 결정적 코드가 한다(CLAUDE.md 2번).
