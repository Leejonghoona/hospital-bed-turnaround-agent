이 에이전트가 하는 일

병원은 환자가 퇴원해도 침대가 바로 비지 않습니다. 퇴원약, 수납, 이송, 청소를 거치는 몇 시간 동안 다음 환자는 기다립니다.

이 에이전트는 퇴원이 정해지면 다음 환자를 미리 연결하고, 늦어지는 단계를 먼저 찾아 담당자에게 알립니다. 확인이 필요한 결정만 사람에게 넘기기 때문에 병상관리 담당은 예외 사례만 보면 됩니다.

세 구간의 이벤트 연쇄

1. 퇴실 전

퇴원 확정에서 퇴실까지

  • 퇴원 예정 등록 누락과 변경을 감지해 병동에 확인 요청
  • 퇴원약, 수납, 교육 대기를 담당 부서 화면에 다음 환자 대기 정보로 공유
  • 보호자 도착 예정 시각을 반영하고 지연 사유를 코드로 기록

사람: 퇴원약 조제 순서(약제), 보호자 연락과 퇴원 교육(병동)

2. 병상 준비

퇴실에서 병상 준비 완료까지

  • 전날 청소 예정표를 공유하고 실제 퇴실 시 청소 요청 확정
  • 완료 신호로 준비 시각을 확정하고, 늦어지면 다시 추정

사람: 청소와 소독 인력 배치(환경), 침상 정리(간호조무사나 병동지원인력, 병원별 설정)

3. 입실

병상 준비에서 다음 환자 입실까지

  • 사전 매칭과 재매칭 제안, 입원 취소 반영
  • 병동에 수용 가능 여부 문의, 입실 부하와 근무 인력 표시

사람: 수용 가능 회신(책임간호사), HIS 확정과 입실 안내(원무), 담당 검토(병상관리 담당)

현장 AX 3단계, 사람 개입

사람 개입 지점

확인 등급별 경로

  • 자동: 대기 정보 공유, 준비 시각 재추정, 청소 예정표 갱신과 청소 요청 발송은 사람 없이 실행
  • 병동 확인: 1단계는 병상관리 담당 확인 뒤, 2단계로 승격된 유형만 담당 확인 없이 병동에 수용 가능 여부 문의. 수용 가능 회신이면 원무가 HIS 확정, 수용 불가 회신이면 사유와 재매칭 후보 2개를 병상관리 담당에게 전달
  • 담당 검토: 병상관리 담당 검토 뒤 병동에 수용 가능 여부 문의
  • 환자 연락이 되돌릴 수 없는 분기점. 연락 전 취소는 보상 단계(퇴실 전이면 청소 예정표 항목과 사전 매칭, 퇴실 후면 확정된 청소 요청을 되돌리는 절차)가 자동 해제, 연락 후 취소는 담당 검토로 바꾸고 재연락을 사람 작업으로 생성

담당 검토로 분류하는 사례

  • 격리 오더 환자, 감염 선별검사 결과 대기 (선제 격리)
  • 중환자실 하향 전동, 응급실 입원 대기 (우선순위 상위)
  • 소아, 낙상과 섬망 위험이 높은 환자
  • 1인실과 상급병실 희망 (병실료 차액 동의)
  • 동명이인, 조건에 맞는 병상 없음, 1·2순위 점수 차가 정책 파일 기준값 미만인 매칭
  • 간호·간병통합서비스 병동 배정 (환자 동의 필요)
  • 격리 퇴실 병실에 다음 환자를 매칭하는 건 (청소 요청은 종말소독 유형으로 자동 발송, 소독 확인 전 매칭 확정과 빈 병상 전환 금지)
  • 성별, 진료과, 격리 여부 입력 누락

도구조회, 계산, 검증, 행동 제안(매칭, 청소 요청, 정보 공유). 기존 규칙과 SHACL 코드를 재사용배정 규칙은 이미 검증된 방식이라 LLM이 다시 만들지 않음
실행 게이트웨이판단에 쓴 정보가 바뀌었는지 제안 시점과 원무가 확정 버튼을 누른 직후에 두 번 확인하고 바뀌었으면 거부. 기술 방식: 이벤트 순번 비교, HIS 쓰기는 원무 승인 값을 실어 FHIR If-Match 버전 검사. 그 밖에 SHACL 재검사, 격리 오더가 있으면 청소 유형을 종말소독으로 강제, 정책 파일로 확인 등급과 권한 판정, 같은 요청은 한 번만 실행, 감사 로그승인을 기다리는 몇 시간 사이 격리 오더가 추가되면 확정 직전에 거부하고 담당 검토로 재분류
사람확인 등급에 따라 병동 회신, 병상관리 검토, 원무 확정, 인계, 에스컬레이션병상 원장은 HIS, 확정 책임은 승인자
평가 하네스이벤트 재생 트윈, 회귀 시나리오, 병원 적용 시 섀도 모드실제 HIS 없이 하루를 다시 돌려 안전하게 검증
관측성사례마다 모델, 프롬프트, 정책 버전, 도구 호출을 trace로 기록"왜 이 병상인가"를 나중에 재현
설계 판단LLM을 빼도 규칙 모드로 운영되고, 진행 상태는 사례 워크플로에, 확정은 게이트웨이와 HIS에 둠

DB

원천 데이터와 상태 변화를 저장합니다. 이벤트는 고치지 않고 추가만 하는 기록으로 SQLite에 두고, 현재 상태는 이 기록을 다시 계산해 만듭니다.

온톨로지

개념 사이의 관계를 정리한 지도입니다. 관계를 한 번 적어 두면 규칙을 하나하나 코드로 쓰지 않아도 프로그램이 연결합니다.

내부망 보안

병원 내부망

서버, DB, 온톨로지, LLM을 병원 서버실에 둡니다. 병원 안 프로그램끼리 쓰는 API는 내부망 밖으로 나가지 않습니다. 외부 환경 업체에는 병상 번호, 예상 시각, 청소 유형만 보내고 환자 정보는 보내지 않습니다.

로컬 LLM

에이전트는 병원 서버의 오픈 가중치 LLM을 씁니다. 운영에서는 외부 AI API를 쓰지 않고, 외부 모델 비교는 개발 단계에서 가상 데이터로만 합니다. 후보와 근거는 모델 선정에 정리했습니다.

권한과 기록

도구 권한은 사례와 행동 단위로 짧게 발급하고, 매칭, 회신, 취소는 모두 감사 로그에 남깁니다.

모델

모델 선정과 배치

LLM은 판단, 설명, 자유 서술 추출만 맡습니다. 배정과 숫자 계산은 도구가 하고, LLM을 빼도 규칙 모드로 돕니다. 그래서 모델은 "가장 똑똑한 것"이 아니라 데이터가 병원 밖으로 나가지 않으면서 세 역할을 안정적으로 해내는 것을 고릅니다.

추출 LLM

병동 전달사항, 보호자 통화 메모 → 정해진 필드

  • 출력: 보호자 도착 예정 시각, 지연 사유 코드, 격리 언급 여부(참고용)
  • 필요 능력: 한국어 구어·축약어 이해, 스키마 그대로의 JSON
  • 호출: 사례당 약 5회, 짧은 입력
  • 추론 모드 끔. 작은 모델이 적합

계획 에이전트

사례 상태 관찰 → 도구 선택 → 행동 제안과 근거

  • 출력: 제안, 근거, 판단에 쓴 이벤트 순번
  • 필요 능력: 다단계 도구 호출, 근거 서술, 같은 입력에 같은 판단
  • 호출: 사례당 약 10회, 도구 결과 포함 입력
  • 추론 모드 켬. 중형 모델

질의 응답

병상관리 담당 질문 → 조회 도구 → 근거 레코드와 답

  • 조회 도구만 사용, 쓰기 권한 없음
  • DB에 없는 사실을 답하면 기능을 끔 (PoC 중단 기준)
  • 호출: 근무조당 수십 건
  • 계획 에이전트와 같은 모델 공유
