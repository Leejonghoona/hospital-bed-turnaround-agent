# FHIR 정렬 제안 검토 (실용주의 테크 리드)

## 0. 먼저 확인한 사실
- 규모: 커밋 25개, `src` 약 3,000줄, `tests` 약 2,000줄(매개변수화로 457개), 시나리오 YAML 38개(dev 30, 홀드아웃 포함).
- `sim` 모델이나 `events` 모델을 직접 쓰는 곳: `events/replay`, `saga/machine`, `gateway/gateway`, `ontology/graph·validate`, `evaluation`의 6개 모듈, 테스트 8개 파일. 정본 형식을 바꾸면 사실상 전부 영향을 받는다.
- 설계 문서는 이미 FHIR 매핑을 갖고 있다. 개념→리소스 표(Patient/Encounter, Location의 physicalType·partOf, Task, Flag+SNOMED 409524006/409529001/409525007), 사가는 "FHIR Task 상태", 게이트웨이는 "가상 FHIR 서버에 If-Match"다. DECISIONS.md(LP-16 계열)에는 "표준 코드 표현은 설계에 적는다. 실제 FHIR 연동은 범위 밖"이라고 적혀 있다.
- 결론부터 말하면 "FHIR을 알고 설계했다"는 증거는 이미 문서에 있다. 비어 있는 것은 실행되는 증거다. 그 빈칸을 메우는 데 정본 교체는 필요 없다.

전제도 하나 바로잡는다. "병원 데이터가 FHIR로 저장된다면"은 현실과 조금 다르다. 국내 HIS는 대부분 자체 스키마이고, FHIR는 교환 계층(API, 구독)으로 붙는 경우가 많다. 그렇다면 FHIR를 **입력 경계**에 두는 쪽이 현실 구조와 맞고 설명도 정직하다.

## 1. 선택지별 비용

| 선택지 | 바뀌는 곳 | 새 코드·테스트 | 커밋 | 기존 457개 / 시나리오 26개 |
|---|---|---|---|---|
| a 안 함 | 없음 | 0 | 0 | 영향 없음 |
| b 입력 경계만 FHIR | 새 `src/turnaround/fhir/`(합성 병원 → R4 Bundle 내보내기, Bundle → 내부 이벤트 어댑터), `sim/__main__`에 옵션 하나 | 400~700줄. 왕복 테스트, 골든 번들, 이중 실행 비교 | 4~6개(2~3일) | 수정 0. 어댑터 경로로 같은 결과가 나오는지 추가로 검증 |
| c 온톨로지까지 FHIR RDF/SNOMED | `concepts.ttl`, `shapes.ttl`, `graph.py`, `validate.py`, 게이트웨이 SHACL 재검사 경로, 불변 조건 검사기 | 셰이프 재작성, `test_ontology`·게이트웨이 SHACL 테스트 재작성 | 8~12개(1~1.5주) | 온톨로지·게이트웨이 테스트 수십 개 재작성. A·B·F 계열 안전 시나리오의 결과가 흔들릴 수 있음 |
| d 전면 FHIR 서버 | sim, events/replay, saga, gateway, evaluation 전부, 시나리오 fixture | 서버 기동(HAPI 등), 저장소 이중화 또는 교체 | 20개 이상(지금까지 한 일과 맞먹음) | 대부분 다시 써야 함. 점수판 이력의 연속성이 끊김 |

c에는 숨은 비용이 있다. FHIR RDF는 인스턴스 직렬화 형식이지 도메인 온톨로지가 아니다. "공기주의는 음압격리실만" 같은 규칙을 FHIR RDF 경로(`fhir:Location.physicalType/fhir:coding/...` 값 노드)로 쓰면 셰이프가 몇 배 길어진다. 게다가 FHIR physicalType에는 음압격리실 개념이 없다. 결국 `ta:NegativePressureRoom` 같은 자체 개념이 그대로 필요하다. 비용은 크고 얻는 것은 적다. SNOMED CT를 전면 정렬하려면 라이선스(국가 회원 여부)와 용어 서버도 확인해야 한다. 데모에서는 문서에 이미 있는 코드 3개 정도로 제한하는 것이 안전하다.

d는 "pytest 한 번, API 키 없이 재현"이라는 지금 프로젝트의 가장 큰 장점을 깨뜨린다. 외부 서버가 필요해지기 때문이다.

## 2. 일정 위험
- 이 프로젝트의 이름은 "에이전트"인데, 7단계(계획 에이전트, 도구, 추출 LLM, LLM 교체 인터페이스, 가짜 LLM)가 아직 없다. 시나리오 26/30도 남은 4개가 7단계 의존일 가능성이 높다. FHIR 작업을 먼저 하면 포트폴리오가 "표준 변환 파이프라인과 규칙 엔진"으로 읽힌다. 핵심 주장(판단은 에이전트, 실행은 게이트웨이)의 실행 증거가 없는 상태로 기한을 맞게 된다.
- 7단계는 FHIR에 의존하지 않는다. 에이전트 도구는 내부 모델을 읽고, 어댑터가 경계를 격리하기 때문이다. 그래서 FHIR를 먼저 해서 얻는 이득은 없고 지연 위험만 있다.
- 홀드아웃은 "4단계, 7단계 끝에만" 돌리기로 했다. 정본을 건드리는 작업이 7단계 앞에 끼면 마일스톤 비교의 기준이 흐려진다.

권장 순서:
1. 7단계
2. 7단계 마일스톤 홀드아웃 실행
3. 5단계 잔여(규칙 모드 기준선, 모델 비교). 에이전트의 가치를 숫자로 보여주려면 필수다.
4. **b를 시간 상한 3일로**
5. 8단계 몬테카를로
6. 9단계 화면. 화면에서 FHIR 번들 입력을 보여주면 b의 효과가 극대화된다.

## 3. 품질 위험과 방지책
- **정본은 내부 이벤트로 유지한다(부패 방지 계층).** 사가·게이트웨이·평가기는 FHIR를 모르게 둔다. 이것만 지켜도 c·d의 회귀 위험은 대부분 사라진다.
- **스냅숏과 이벤트의 불일치(가장 실질적인 함정).** FHIR 리소스는 상태 스냅숏이다. 그런데 이 시스템은 `occurred_at`과 `observed_at`의 분리(EV-01 인지 지연), 중복 도착, 완료 신호 누락 같은 이벤트 의미에 기대고 있다. 현재 상태 번들만 받으면 중간 상태와 인지 시각이 사라지고, S4 누수 검사가 무의미해진다. 그래서 어댑터 입력은 리소스 버전 이력을 담은 `Bundle.type=history`(또는 transaction 연속)로 하고, `meta.lastUpdated`와 `Task.executionPeriod`, `statusReason`을 이벤트의 두 시각에 명시적으로 대응시킨다. 이 대응표는 DECISIONS.md에 먼저 적는다.
- **계약 테스트**
  - 왕복 테스트: 합성 병원 → Bundle → 내부 모델이 원래와 같아야 한다.
  - 골든 번들 스냅숏 테스트
  - R4 기본 구조 검증: `fhir.resources`를 테스트 의존성으로만 쓴다. KR Core 프로파일 검증은 Java 검증기가 필요하므로 "하지 않음"으로 명시한다.
- **이중 실행 비교**
  - 시드 0~199에서 "생성기 → 이벤트"와 "생성기 → FHIR → 어댑터 → 이벤트"가 같은 이벤트 스트림 해시를 내야 한다.
  - 점수판 지표(S1/S2/S4, P50·P90)가 같아야 한다.
  - 시나리오 결과가 26/30으로 같아야 한다.
  - 하나라도 다르면 병합하지 않는다.
- 잡음 주입은 어댑터 뒤(이벤트 단계)에 유지한다. 잡음을 FHIR 번들에 넣으면 변수가 둘이 되어 원인 분리가 어렵다.

## 4. CLAUDE.md·설계와의 충돌

| 원칙 | b | c | d |
|---|---|---|---|
| 합성 데이터만 | 문제없음(자체 생성기 사용. Synthea도 불필요) | 문제없음 | 문제없음 |
| "설계/제외" 미구현 | 문제없음. 설계 문서 매핑 표를 실행할 뿐 | 일부 확장. 문서 매핑 표 범위를 넘음 | "실제 HIS 쓰기 연동" 제외와 경계가 모호해짐. 구조도의 "FHIR 구독"까지 끌려옴 |
| DECISIONS "실제 FHIR 연동은 범위 밖" | 파일 기반이라 위반 아님 | 위반 아님 | 사실상 위반 |
| 우선순위 9단계 | 7단계 뒤에 넣으면 무난 | 6단계 재작업 | 전 단계 재작업 |

어느 선택지든 CLAUDE.md 규칙상 **코드보다 먼저 DECISIONS.md에** 이유, 범위, 비목표(서버·구독·KR Core 프로파일 검증·SNOMED 전면 정렬 제외)를 적어야 한다.

## 5. 권고
**b를 택한다. 7단계 뒤에, 시간 상한 3일로 한다. c는 "매핑 트리플" 수준으로만 한다. d는 하지 않는다.**

최소 비용으로 포트폴리오 효과를 내는 묶음(합계 5~7커밋):
1. **b 어댑터와 이중 실행 비교.** "정본은 그대로 두고 표준 경계를 붙였으며, 시드 200개와 시나리오 26개에서 결과가 같음을 증명했다"는 한 줄은 ai-dd 포트폴리오에서 FHIR 자체보다 강한 신호다. AI가 만든 변경을 계약 테스트로 묶어 통제했다는 증거이기 때문이다.
2. **c-lite.** `concepts.ttl`에 `skos:exactMatch`(예: `ta:AirborneIsolationPatient` → SNOMED 409524006)와 `ta:Bed` → FHIR Location 대응 트리플 10줄 안팎을 추가한다. 기존 셰이프는 건드리지 않는다. FHIR 번들에서 만든 그래프가 같은 SHACL을 통과하는지 보는 테스트 1개를 둔다.
3. **DECISIONS.md 한 항목: "왜 FHIR를 정본으로 하지 않았나".** 스냅숏과 이벤트의 차이, FHIR physicalType에 음압실이 없다는 점, 재현성을 근거로 쓴다. 리뷰어는 "FHIR 기반 온톨로지"라는 주장보다 이 판단 근거를 더 높게 평가한다.

피해야 할 표현: "FHIR 기반 온톨로지", "FHIR 호환 시스템". 정확한 표현은 "FHIR R4 입력 어댑터(합성 데이터, R4 기본 구조 검증, KR Core 프로파일 미검증)"다.

중단 조건: b가 3일 안에 이중 실행 동등성을 통과하지 못하면 어댑터를 내보내기 전용(내부 → FHIR 번들 출력)으로 축소한다. 내보내기만으로도 화면 시연과 매핑 증거는 확보된다.
