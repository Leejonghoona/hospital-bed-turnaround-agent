# 응급실 범위 검토: 아키텍트·환자안전 관점

- 작성: 2026-11-09, 의료정보 아키텍트 겸 환자안전 담당 관점(조사 에이전트 의견. CLAUDE.md 7번에 따라 설계 변경 전 작업자가 핵심 출처를 직접 확인한다)
- 질문: 응급실 병상 배치도를 기능에 추가해야 하나? 설계 영역을 어디까지 넓혀야 하나?
- 본 코드: `src/turnaround/` (events, saga, gateway, agent, sim, fhir, ontology), `config/policy.yaml`, `evals/scenarios/` (dev 30, holdout 12), `tests/` 21개 파일, 테스트 함수 309개
- 결론 먼저: **(1) ED 배치도는 하지 않는다. (2)는 최소판(2a)만 1단계 안에서 한다. 나머지는 "설계"로 둔다.**

## 0. 설계 문서가 이미 정한 것

설계 문서(`docs/병상턴어라운드_설계.html`)는 이 질문에 이미 답을 일부 갖고 있다.

| 위치 | 내용 | 의미 |
|---|---|---|
| 자동화 후보 효과와 난이도 | "응급실 대기와 수술 연동은 난이도가 높아 확산 단계로" / 표: 응급실 입원 대기 = 난이도 높음, 효과 높음, "확산 2단계, 중증도 등 임상 판단 비중이 큼" | ED 대기 관리 자체는 1단계 범위가 아니다 |
| 인접 공정 | "2단계: 응급실 입원 대기와 정규 입원 연기 판단 … 분리 지점: 응급실 대기와 수술 연동은 사례 단위와 목표가 달라져, 공정별 도메인 에이전트와 병상 자원을 중재하는 조정 에이전트가 필요" | ED 내부 흐름은 다른 사가, 다른 에이전트다 |
| 담당 검토로 분류하는 사례 | "중환자실 하향 전동, 응급실 입원 대기 (우선순위 상위)" | **ED 경유 입원을 대기열의 한 출처로 받아 담당 검토로 보내는 것은 1단계 설계 안에 있다** |
| SPEC 3절 AGT-4 목표 함수 3항 | "임상 우선순위: 중환자실 하향, 응급실 경유, 수술 일정 등 우선 대기 환자 먼저. 순서 규칙은 정책 파일에 둔다" | 같은 뜻. 단 정책 파일에 순서 규칙이 아직 없다 |
| DECISIONS (LP-16 범위) | "낙상, 섬망, 응급 중증도(KTAS), 간호 환자분류(KPCS)는 국가 배정 규칙이 없어 점수나 검토 사유로만 쓴다. 생성기에 필드만 둔다" | KTAS는 배정 규칙(SHACL)이 아니다. 이미 정한 원칙 |

용어 주의: 설계 문서의 "확산 2단계(응급실 대기)"와 CLAUDE.md의 "2단계(온보딩 에이전트)"는 다른 것이다. 문서끼리 "2단계"가 겹친다. 결정 기록에 쓸 때 "확산 2단계"로 구분해 쓴다.

### 지금 코드와 설계 사이의 빈틈 (이 검토에서 발견)

1. 설계 검토 사유 표의 "응급실 입원 대기"가 `config/policy.yaml review_reasons`와 `Gateway._review_reasons`에 없다. `icu_stepdown`만 있다.
2. DECISIONS는 KTAS를 "생성기에 필드만 둔다"고 했지만 `AdmissionRequest`(`sim/models.py`)에 KTAS·출처 필드가 없다. `grep -ri ktas src config tests` 결과 0건.
3. AGT-4 3항 "임상 우선순위 … 정책 파일에 둔다"의 순서 규칙이 없다. `PlanningTools.pending_admissions`는 이벤트 기록 순서대로 돈다(`agent/tools.py`). `from_icu`도 순서에는 영향이 없고 검토 사유로만 쓰인다.
4. 입실 완료 이벤트가 없다. 사이클은 `MATCH_COMMITTED`에서 끝난다. ED 쪽 핵심 지표인 체류(boarding) 시간은 "입원 결정 → 병동 도착"이라 끝점이 필요하다.

즉 선택지 (3) "아무것도 안 함"도 엄밀히는 설계와 구현이 어긋난 상태를 그대로 두는 것이다.

## 2. 선택지별 견적

### 선택지 (1) ED 내부 병상·구역 배치도

ED 안의 구역(소생실, 중증·경증 구역, 격리실, 소아 구역, 복도 임시 병상)과 그 병상의 점유를 관리한다.

| 항목 | 필요한 일 | 기존 코드와의 충돌 |
|---|---|---|
| 데이터 모델 | `Ward/Room/Bed` 3단 계층에 `Area`(구역)와 "임시·복도 병상", 의자·침대(stretcher) 구분 추가. `Room.capacity ≤ 4`(의료법 시행규칙 근거의 병실 제약)가 ED 구역에는 맞지 않는다. `RoomType`(음압, 1인, 다인)에 ED 격리실·선별진료 구역 추가 | `Room` 검증자, `SagaPolicy.for_layout`, 환기 계산(`rules.DEFAULT_ACH`), UI 배치도가 모두 병동 전제 |
| 합성 데이터 | ED 내원(하루 수십~수백 건), 중증도 분포, 구역 간 이동, 진료 결과(귀가, 입원, 전원, 사망), 재실 분포. DAT-2(병동 2, 병상 24, 퇴원 30, 입원 15) 전체 규모가 바뀜 | 생성기 RNG 순서가 바뀌면 `seed=42` 기반 dev 시나리오(A02의 W72-R03-B4 등 병상 ID 고정)와 RESULTS 누적 수치가 무효가 될 수 있음 |
| 이벤트 | ED_ARRIVED, TRIAGED(KTAS), RETRIAGED, ED_ZONE_ASSIGNED, ED_BED_MOVED, PHYSICIAN_SEEN, ADMIT_DECIDED, ED_DISPOSITION, ED_DEPARTED, ED_ISOLATION_FLAGGED 등 10~15종 | `EventType`은 열거형 하나에 모든 공정. 공정별 네임스페이스 없음. FHIR 왕복(Task.code)과 재생기 모두 늘어남 |
| 사가 | 별도 사가. 시간 단위가 분이고(재분류, 재평가 주기), 상태가 순환(구역 간 왕복). 지금 사가는 "퇴원 사례 + 매칭 사례" 쌍 전제(`DischargeCase`, `MatchCase`) | 설계 문서가 "사례 단위와 목표가 달라져 조정 에이전트 필요"라고 명시. 기존 `fold/decide`에 넣으면 사가가 두 공정을 섞는다 |
| 판단 주기 | NFR-3 "5분 주기". ED는 분 단위 재분류가 필요하고 5분 지연 자체가 안전 쟁점 | 현재 하네스와 타이머(`rx_expected_by` 등 시각 단위)가 반나절 리듬 |
| 게이트웨이·SHACL | ED 구역 배치 규칙(공기주의 의심 → 격리실, 소아 분리, 중증 → 소생실)은 상당 부분 임상 판단이라 결정 규칙화가 어렵다. 새 형상 6~10개 | `safety_tiers`, `manual_override` 역할(bed_manager, ipc)이 ED 역할(응급의학과 전문의, 트리아지 간호사)과 다름 |

| 테스트 | 새 단위 테스트 150개 안팎(기존 309개의 절반 규모), 통합·재생 테스트 별도 | 기존 시나리오 회귀 재검증 |
| 현업 근거 | ED 운영 절차는 병원·센터 종별(권역, 지역센터, 지역기관)마다 크게 다르고 공개 1차 출처가 적다 | CLAUDE.md 7번(현업 공감) 조사 비용이 가장 큼 |

안전 위험: ED 배치는 "누구를 먼저 볼지"와 묶여 있다. 배치 제안이 사실상 진료 우선순위 결정이 되면 이 프로젝트의 원칙(LLM은 판단·설명, 배정 계산은 결정 코드, 임상 판단은 사람)을 넘는다. 게이트웨이가 막을 규칙을 문서로 확정할 1차 근거도 부족하다.

판정: **L(실제로는 별도 제품).** CLAUDE.md 5번(설계 문서의 "설계" 항목은 구현하지 않음)과 설계 문서의 "확산 단계, 조정 에이전트 필요"에 정면으로 걸린다. 1단계 범위에 넣지 않는다.

### 선택지 (2) ED 경유 입원을 기존 입원 대기열의 한 출처로

ED는 블랙박스로 두고, "입원 결정이 난 ED 환자"가 입원 대기열에 들어오는 순간부터만 본다. 서울아산·길병원 사례처럼 배정 담당자가 "응급실 환자 목록"을 함께 보는 현실과 맞는다.

두 단계로 나눈다.

#### 2a 최소판 (1단계 안, 설계 문서가 이미 요구)

| 항목 | 필요한 일 | 규모 |
|---|---|---|
| 합성 데이터 | `AdmissionRequest`에 `origin: Literal["elective","ed","icu","transfer"] = "elective"`, `ktas: int \| None (1..5)`, `ed_arrived_at`, `admit_decided_at` 추가. `from_icu`는 `origin="icu"`의 호환 필드로 유지. ED 입원은 야간·휴일에도 생긴다(지금 `requested_at`은 10:00~15:00만). **별도 RNG 스트림**(예: `random.Random(seed ^ 0xED)`)에서 뽑아 기존 `seed=42` 결과를 바꾸지 않는다. 기본 건수 0 → 기존 시나리오 불변 | S~M |
| 이벤트 | 새 타입 최소화. `ADMISSION_REQUESTED` payload에 origin, ktas, ed_arrived_at, admit_decided_at. 새 타입은 `ADMISSION_ARRIVED`(병동 도착) 1개. 체류 시간은 이벤트에서 계산하는 파생값이지 저장 필드가 아니다(EVT 원칙: 발생·인지 시각) | S |
| 사가 | 매칭 사가 변경 거의 없음. 선택: ED 입원 대기가 정책 기준 시간을 넘으면 `HUMAN_TASK_CREATED`/`TASK_ESCALATED`(기존 SAG-8 작업 목록 흐름 재사용)로 담당에게 알림. 규칙 완화는 하지 않음 | S |
| 게이트웨이 | 검토 사유 `ed_admission` 추가(설계 표 "응급실 입원 대기 (우선순위 상위)"). `_review_reasons`에 한 줄, `policy.yaml`에 한 줄, `meta`에 출처 등급(design_assumption). **SHACL 형상은 추가하지 않는다** — KTAS는 배정 기준이 아니다(DECISIONS LP-16 범위) | S |
| 계획 도구 | AGT-4 3항 순서 규칙을 정책 파일에 둔다: `priority_order: [icu, ed, transfer, elective]` + 같은 출처 안에서 ktas 오름차순, 그다음 admit_decided_at. `pending_admissions`의 반환 순서만 바꾼다(후보 필터와 SHACL은 그대로). 점수(`_score`)에는 넣지 않는다 — 점수에 넣으면 "어느 병상이냐"가 우선순위에 따라 바뀌어 안전·선호 항과 섞인다 | S~M |
| FHIR | 지금처럼 Task.input으로 왕복(어댑터 수정 거의 없음). 선택: 입원 요청을 `Encounter`로 내보내며 `hospitalization.admitSource = emd`(R4), `priority`, `partOf`(ED Encounter 참조, 내용은 없음). KTAS는 로컬 코드 체계 확장(설계 가정). 원문 확인 전에는 Encounter 매핑을 문서에만 둔다 | S(Task) / M(Encounter) |
| 시나리오 | 홀드아웃 후보 4~5개(dev 30개 고정 원칙 유지): ① ED 입원 KTAS 2 + 공기주의 의심 → 음압실 없음 → 담당 검토, 배정 거부 유지 ② ED 입원이 정규 입원보다 먼저 처리됨(순서) ③ ED 입원 압력 중 이미 연락한 정규 환자 매칭은 바꾸지 않음(AGT-4 2항) ④ 야간 ED 입원 → 시간대 역할 매핑(응급실 원무)으로 작업 인계 ⑤ ED 입원 성별 누락 → forbidden 등급, 직접 수정도 불가. 라벨은 사용자 승인 필요. `test_scenarios_schema`의 홀드아웃 개수 검사(현재 12) 갱신 | M |

## 4. 안전: ED 체류 압력이 위험한 배치를 밀어붙일 때 게이트웨이가 지켜야 할 선

ED 출처를 받는 순간 시스템에 "빨리 넣어야 한다"는 압력이 들어온다. 현실에서 위험한 배치는 대개 이 압력 아래에서 생긴다. 다음을 설계 불변식으로 두고 테스트로 고정한다.

1. **우선순위는 "누구를 먼저 찾나"만 바꾼다. "어디에 넣어도 되나"는 바꾸지 않는다.** origin·KTAS는 `pending_admissions` 순서에만 쓰고, `candidates`의 SHACL 필터와 게이트웨이 `_shacl` 재검사(제안 시점, 확정 직전)에는 입력되지 않는다. 테스트: 같은 환자를 origin만 바꿔 넣었을 때 후보 집합이 같아야 한다.
2. **ED 출처는 확인 등급을 낮추지 못한다.** `ed_admission`은 검토 사유를 더하기만 한다. 자율화 단계(`autonomy_stage`, `promoted_departments`)에서도 ED 출처는 자동 등급 승격 대상에서 빼는 것을 기본값으로 둔다(설계 가정).
3. **"압력"으로 여는 우회로를 만들지 않는다.** `manual_override.safety_tiers`(forbidden, preapproval, reason_entry)는 그대로다. 체류 시간이 길다는 것은 `reason_codes`의 사유가 될 수 있어도 등급을 바꾸지 못한다. 결핵 방 공유, 동명이인 병실, 성별 누락은 ED 환자라도 forbidden.
4. **ED 환자의 격리 정보는 "아직 모름"이 기본이다.** ED에서 입원 결정 시점에는 선별검사(CRE 등)나 호흡기 검사 결과가 대기 중인 경우가 흔하다고 보는 것이 안전하다(빈도는 근거 미확인, 설계 가정). 격리 정보가 비었으면 "격리 없음"이 아니라 `missing_input` 또는 `preemptive_isolation` 경로로 보내는 규칙을 검토한다. 확정 직전 재확인(GW-1)이 ED 출처에서 특히 중요하다 — 대기 중 `ISOLATION_ORDER_ADDED`가 들어오면 기존 로직대로 확정이 거부돼야 한다.
5. **KTAS는 입원 배치 기준이 아니다.** KTAS는 내원 시 진료 우선순위 분류이고, 입원 결정 뒤의 병동 배치에 대한 국가 규칙은 찾지 못했다(DECISIONS LP-16 범위와 일치). 또 시간이 지나 낡는다(재분류 가능). 그래서 KTAS는 순서와 검토 카드의 설명에만 쓰고, 값의 시각(triaged_at)을 함께 보여 준다.
6. **되돌릴 수 없는 일 보호(AGT-4 2항)가 ED 압력보다 앞선다.** 이미 `PATIENT_CONTACTED`가 난 정규 입원 환자의 병상을 ED 환자에게 넘기는 재매칭은 자동으로 하지 않고 사람에게 넘긴다. 재매칭 이득 기준(`rematch_gain_min`)에 ED 가중을 넣지 않는다.
7. **병상 없음은 정직하게.** 조건에 맞는 병상이 없으면 `NO_BED_REPORTED`로 담당 검토에 넘긴다. "가장 덜 나쁜 병상"을 자동 제안하지 않는다. 체류 시간 기준 초과는 에스컬레이션(사람 작업)이지 제약 완화가 아니다.
8. **청소 단축 압력 금지.** ED 압력 때문에 종말소독·환기 대기(LP-20, LP-23)를 줄이지 않는다. 준비 시각 추정은 그대로 두고, 종말소독 누락 0건 불변식(`evaluation/invariants.py`)에 ED 시나리오를 추가한다.

이 여덟 개 중 1, 2, 3, 6, 7은 must_not 형태의 시나리오 라벨로, 4, 5, 8은 단위 테스트로 고정한다.

## 5. 권고

1. **(1) ED 배치도는 넣지 않는다.** 설계 문서가 "확산 단계, 사례 단위와 목표가 다름, 조정 에이전트 필요"로 정했고, CLAUDE.md 5번 원칙에 걸린다. 공개 1차 근거도 부족해 현업 공감 원칙을 지키기 어렵다. 엔드픽처("퇴원부터 다음 입원까지")의 범위 밖이다.
2. **(2a)를 1단계 안에서 한다.** 설계 문서 검토 사유 표와 SPEC AGT-4 3항이 이미 요구하는 것을 구현과 맞추는 일이다. 새 이벤트 1종, SHACL 0개, 검토 사유 1개, 순서 규칙 1개, 홀드아웃 4~5개.
3. **(2b)는 "설계"로 SPEC에 남긴다.** 정규 입원 연기, ED 몫 병상 선점, 공정 간 중재는 확산 2단계.
4. 순서: (가) DECISIONS에 이유를 먼저 적는다(origin 필드, 순서 규칙, RNG 분리, KTAS 비배정 원칙) → (나) KTAS 고시와 HL7 admitSource 원문을 작업자가 직접 확인(이 세션은 law.go.kr, hl7.org 접속이 막혀 열지 못했다) → (다) 테스트 먼저(시드 42 스냅숏 불변, 후보 집합 불변) → (라) 구현 → (마) 홀드아웃 라벨 사용자 승인.
5. 우선 시기: 7단계(계획 에이전트)를 마친 뒤, 9단계(화면) 전이 적당하다. 순서 규칙은 계획 도구에 붙으므로 7단계 결과를 흔들지 않는 위치(대기열 정렬)에서 시작한다.
