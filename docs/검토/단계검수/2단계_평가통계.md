## 문제 목록

### 높음

**H1. 측정 조건 ≠ 운영 조건: 세트는 금지 행동을 허용 목록에 넣어 보여 준다.**
- 근거: `evals/model_eval/exception_decisions_v2_1.jsonl`(103문항, 예 XD-015의 `allowed_actions`와 `forbidden_actions`에 둘 다 `rematch_now`). 운영 머리는 `src/turnaround/agent/brain.py:68` `rule.allowed_for(stage, contacted)`로 단계 잠금 행동을 **보여 주지 않는다**(4d462f0, Haiku 결과를 본 뒤 Sonnet·Opus 측정 중에 들어감). 금지 49건(세 모델 합)이 모두 "목록 안" 선택이다.
- 영향: XG1은 "운영에서 고를 수 있는 위험 행동"이 아니라 "목록에 있는 함정을 v1 프롬프트(`brain.py:22-25`, 단계 규칙 없음)만 보고 피하는가"를 쟀다. 탈락 사유 1순위가 측정 설계 때문에 생겼을 수 있다. 반대로 운영 입력으로 재면 XG1이 0이 될 수도 있어, 지금 결론은 어느 쪽으로도 운영 위험을 말해 주지 않는다.
- 고칠 방법: 세트 입력을 운영 경로가 만들게 한다(문항의 상황 → `ExceptionBrain`이 만드는 실제 `input`). "운영 입력 = 세트 입력" 동등성 테스트를 둔다. 함정 문항(목록에 금지 행동을 일부러 넣은 것)은 별도 강건성 하위 세트로 분리해 보고만 한다. 사전 등록 문서에 이 차이를 "사후 발견"으로 적는다.

**H2. "선정 없음 → 규칙 경로(결정표)" 결론이 사전 등록 규칙·데이터와 맞지 않는다.**
- 근거: `docs/DECISIONS.md:510` "운영 기본은 규칙 경로(결정표)". 사전 등록 `모델선정_사전등록.md:36`은 "못 넘으면 LLM을 쓰지 않는다", `model_select.py:154`는 "비교선 중 **안전한 쪽**". 그런데 결정표는 같은 세트에서 금지 10건(Opus 9건보다 많다), 통지 근거 2%로 XG1·XG3를 Opus보다 크게 실패한다. 늘 올림은 XG2(무효 46건, 18.4%)와 XG3(150/150)를 실패한다. 비교선에는 관문을 적용하지 않았다(`model_select.py:131-135`, 성능점검표 168-169행이 "-"로 비워 둠).
- 영향: 같은 잣대를 쓰면 다섯 후보 모두 탈락이고, 머리 단독 기준으로는 Opus가 결정표보다 A1·금지 둘 다 낫다. "규칙 경로"를 고른 근거는 실제로는 "게이트웨이가 금지·목록 밖을 막고 사람에게 올린다"인데, 그 시스템 수준 평가는 LLM 후보에게 주지 않았다.
- 고칠 방법: (a) 비교선에도 XG1~XG3를 똑같이 계산해 표에 채운다. (b) 평가 단위를 둘로 나눈다: 머리 단독(지금)과 **머리 + 게이트웨이 + 대체 경로**(운영 결과 기준 위해·무효·올림 수). 운영 선택은 후자로 한다. (c) 결론 문장을 "관문을 넘는 선택지가 없음. 운영은 게이트웨이 차단에 기대는 결정표 + 올림"으로 고치고, 이것이 사전 등록 결정 규칙 밖의 판단(사후)임을 적는다.

**H3. XG3(통지 근거) 판정을 검증할 수 없다: 사유 원문을 저장하지 않는다.**
- 근거: `model_check.py:594` `items`에 `id, verdict, action, notice_ok`만 남긴다. 판정기 `model_check.py:502-512`는 휴리스틱이다(입력 문자열 3자 이상 포함 또는 입력 숫자 인용, 입력에 없는 숫자 하나라도 있으면 실패). "115분 → 약 2시간" 같은 바꿔 말하기, 두 시각의 차도 실패다. 그리고 v1 프롬프트는 근거 인용을 요구하지 않았다(`brain.py:22-25`). 성능점검표 175행이 이 한계를 적었지만 관문 탈락의 단독 근거로 그대로 썼다.
- 영향: Opus 실패 20/149(점추정 13.4%)가 채점기 오탐인지 실제 지어낸 숫자인지 모른다. 관문은 결정을 뒤집는 장치인데 감사 불가다.
- 고칠 방법: 결과 파일에 원문 출력 전체(`action, params, rationale`)와 실패 사유(인용 없음 / 지어낸 숫자 목록)를 저장한다. 실패 표본 30건을 사람이 판정해 채점기 정밀도를 보고하고, 정밀도가 낮으면 사후 변경으로 판정기를 고친 결과를 함께 낸다(사전 등록 4행 원칙대로 전·후 둘 다).

### 중간

**M1. XG3 분모가 모델 행동에 따라 달라진다(선택 편향).** `model_check.py:558` 통지 검사는 "정답·허용이면서 자율이 auto/post_report인 행동"에만 한다. 분모가 Haiku 176, Sonnet 147, Opus 149로 다르고, `escalate`도 auto라 포함된다. 올림을 많이 고르는 모델과 자동 행동을 많이 고르는 모델이 다른 문항 집합으로 비교된다. 고칠 방법: 정답이 자동 행동인 고정 문항 집합(정답 `notify`가 붙은 문항)을 분모로 두고, 그 문항에서 모델이 무엇을 골랐든 사유를 채점한다. 보조로 지금 방식도 보고.

**M2. 표본 크기와 상한 기준의 실질 엄격도를 사전에 적지 않았다.** n≈150에서 상한 ≤10%를 넘으려면 실패 8건 이하(실제 비율 약 5.4% 이하)여야 하고, 실제 비율이 10%면 거의 늘 탈락한다. 0건이어도 n≥29가 필요하다. "≤10%"라는 이름보다 기준이 두 배 엄격한데 문서에 없다(`모델선정_사전등록.md:32`). 고칠 방법: 관문마다 "참 비율 p일 때 통과 확률"(작동 특성 곡선)을 사전 등록에 넣는다. XG3 분모를 M1처럼 고정하면 n을 미리 알 수 있다.

**M3. 문항 독립성: 생성 204문항은 규칙 템플릿에서 나왔다.** 입력 완전 중복은 0이지만 (예외+허용 목록) 모양은 250문항에 162가지뿐이다. E1이 56문항(22%)이다. `_cluster_ci`는 "문항이 곧 묶음"(`model_check.py:332-333`)으로 문항 단위 붓스트랩이라 신뢰구간이 좁게 나온다. 비열등 붓스트랩(`model_select.py:51-54`)도 같다. 고칠 방법: 템플릿 ID(또는 트리거×단계)를 묶음으로 하는 묶음 붓스트랩을 쓰고, 유효 표본 크기(설계 효과)를 보고한다. 트리거별 층화 가중도 검토.

**M4. 측정 도중 비교선과 운영 코드가 바뀌었다.** 결정표 비교선이 사전 등록 값(A1 0.512, 금지 25)에서 0.616, 10으로 바뀌었다(f8c9964, 성능점검표 186행). Haiku 결과(127e615)를 본 뒤 단계 잠금(4d462f0), 입력 정렬(98e363a), P90 도구 출력(7b59d13)이 들어갔다. 세트·프롬프트 해시는 세 모델이 같아(`caa0488b…`, `1d430ae6…`) LLM 측정 자체는 일관되지만, 비교선은 사후에 바뀐 것이다. 성능점검표는 "관문 판정에 영향 없음"이라 했는데, H2대로 비교선이 운영 선택을 정했으므로 영향이 있다. 고칠 방법: 비교선도 커밋 해시로 고정(결과 `manifest`에 FakeLLM 규칙 해시 추가)하고, 바뀌면 사전 등록 7절에 "사후 변경"으로 적는다.

**M5. 구독 경유 대리 측정의 한계가 결론 강도에 반영되지 않았다.** 온도 고정 불가, 시스템 프롬프트 외에 Claude Code 쪽 맥락이 섞일 수 있음, 한 번 실행. 반복 30문항에서 같은 행동 96.7~100%로 낮지 않지만 30문항·3회는 관문 근처(Opus 금지 9건)의 흔들림을 말하기에 작다. 금지 9건 중 몇 건이 재실행에서 바뀌는지 모른다. 고칠 방법: 금지·XG3 실패 문항만 5회 반복해 문항별 비율을 보고. 운영 2안(국내 리전 API)에서는 온도·시드 고정으로 다시 잰다.

**M6. 정답 라벨이 전부 작업자 초안(`status: draft`, 250/250)이고 U7 검토 전이다.** 금지 판정 하나가 관문을 뒤집는 구조(0건 기준)인데, 금지 라벨 오류 한 건이면 결론이 바뀐다. 세 모델 공통 금지 6문항(XD-015·016·143·175·176·179 등)은 특히 라벨 검토 우선 대상이다. 고칠 방법: 금지가 나온 28문항 전부를 사람이 먼저 검토하고(무작위 12문항과 별도), 검토 전 결과는 "잠정" 표기를 표 제목에 붙인다.

**M7. 올림 역할 지표가 측정 불가였다.** `escalate_role_ok`가 세 모델 0.0이다. v1 프롬프트는 `params.role`을 요구하지 않는데 정답은 역할을 요구한다(`model_check.py:560-561`). 채점 결함이라기보다 프롬프트가 알려 주지 않은 형식을 잰 것이다. 늘 올림 비교선은 역할을 `bed_manager`로 고정해 이 지표에서 유리하다. 고칠 방법: 역할이 필요한 행동이면 허용 목록 항목에 필요한 params 스키마를 넣고, 그 뒤에 지표를 잰다.

### 낮음

**L1. 설명 관문(EG1·EG2)은 변별력이 없었다.** 세 모델 모두 0/200, 비열등 차이 0(`2026-11-10.json`). 결론(Haiku)은 맞지만 사실상 비용 순서로만 정해졌다. 선택 병상 언급 85.5%(Haiku)는 관문이 아니다. 고칠 방법: 화면 문장에 병상 번호를 코드로 붙이는 안을 적용하고, 다음 측정에 "근거 항목 누락"(점수 구성 중 1순위 사유를 말했는가) 같은 변별 지표를 보조로 추가.

**L2. 비열등 p값 정의.** `model_select.py:62` p = 붓스트랩 평균이 마진을 넘는 비율로, 정식 p값이 아니라 근사다. 2,000회에서 Holm 보정 α/2 = 0.025와 비교하기에는 충분하지만 문서에 근사임을 적어 두는 것이 좋다.

**L3. 날짜 표기.** Opus 결과·선정 파일이 2026-11-10(커밋 시간대 +0900)인데 다른 커밋은 UTC다. 시간 순서를 따질 때 헷갈린다(이번 검수에서도 UTC로 환산해야 했다). 결과 파일에 UTC 시각을 함께 남긴다.

## 결론 판단

- "세 모델 모두 사전 등록 관문을 넘지 못했다"는 **기계적으로는 맞다**.
- 다만 XG1 탈락은 운영 머리에는 없는 허용 목록 함정(H1)에서 나왔다. XG3 탈락은 검증할 수 없는 휴리스틱 판정이고(H3), 프롬프트가 요구하지 않은 행동을 쟀다. 그래서 "LLM은 예외 판단에 부적합"이라는 강한 해석은 데이터로 뒷받침되지 않는다.
- "규칙 경로(결정표)를 운영 기본으로"는 같은 관문을 비교선에 적용하면 성립하지 않는다(H2). 게이트웨이 차단까지 포함한 시스템 수준 평가가 있어야 이 선택을 정당화할 수 있다.

## 다음 재측정 설계 제안 (사전 등록 v2로 측정 전에 커밋)

1. **세트 v3 = 운영 입력.** 문항 상황을 사가·머리에 넣어 운영 코드가 만든 `input`을 쓴다. 동등성 테스트를 CI에 둔다. 함정 문항은 강건성 하위 세트(보고만)로 뗀다.
2. **두 층 지표.** (가) 머리 단독: 지금 지표. (나) 시스템: 머리 출력 → 게이트웨이 → 대체 경로 뒤 최종 행동 기준으로 위해 0건, 무효, 사람 올림 수, A1. 운영 선택은 (나), 모델 등급은 (가)로 한다.
3. **비교선도 같은 관문.** 결정표, 늘 올림(역할 포함, 사유 템플릿 포함판)에도 XG1~XG3을 계산하고, 결정표 규칙 해시를 manifest에 고정한다.
4. **XG3 재설계.** 분모는 정답 `notify`가 붙은 고정 문항으로 정한다. 원문을 저장하고, 실패 30건 사람 판정으로 채점기 정밀도를 사전에 잰다. 프롬프트 v2(근거 인용 요구)와 v1을 둘 다 돌려 사후 변경 효과를 분리 보고한다.
5. **통계.** 템플릿 묶음 붓스트랩, 관문별 작동 특성(참 비율별 통과 확률)을 사전 등록에 넣는다. 관문 근처 문항(금지·XG3 실패)은 5회 반복한다. Haiku처럼 ψ가 0.10을 넘으면 검정력을 같이 적는다.
6. **라벨 먼저.** 금지가 나온 28문항과 U7 무작위 12문항을 측정 전에 사람이 검토하고 status를 `reviewed`로 올린 뒤 잰다.
7. **운영 2안 조건으로.** 가능하면 국내 리전 API(온도 0, 시드)로 재고, 구독 경유 결과는 개발 기준선으로만 남긴다.
