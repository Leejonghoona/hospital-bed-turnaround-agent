## 1. 핵심 원칙 10개

### 원칙 1. "바이브 코딩"과 "에이전트 공학"을 구분하고, 이 프로젝트는 뒤쪽이다
- S1 Karpathy 원문: "I "Accept All" always, I don't read the diffs anymore." / "It's not too bad for throwaway weekend projects, but still quite amusing."
  - 요지: 원래 정의는 diff를 안 읽는, 버려도 되는 주말 프로젝트용 방식이다.
- S2 Willison: "When I talk about vibe coding I mean building software with an LLM without reviewing the code it writes." / "My golden rule for production-quality AI-assisted programming is that I won't commit any code to my repository if I couldn't explain exactly what it does to somebody else."
- S7 Willison: "It's also become clear to me that LLMs actively reward existing top tier software engineering practices"
- 적용: 공개 데모로 남에게 보일 것이므로 "설명할 수 없는 코드는 커밋하지 않는다"를 기준으로 삼는다. 빠른 시제품(와이어프레임 스케치 등)만 바이브 코딩으로 하고, 버린다.

### 원칙 2. 에이전트에게 "통과/실패로 답하는 검사"를 준다. 이것이 속도와 정확성을 동시에 준다
- S14: "Claude stops when the work looks done. If it has nothing to run that tells it whether the work actually *is* done, "looks done" is all it has to go on. In practice that makes you the test suite"
- S14: "Give Claude something it can run that comes back pass or fail. Once it has that, it can keep going on its own and you don't have to watch." 검사 예시에 "A [browser screenshot] next to the mockup"이 들어 있다.
- S12: "Deterministic graders are natural for coding agents because software is generally straightforward to evaluate: does the code run and do the tests pass?"
- 적용: 화면 작업도 "점수"가 아니라 통과/실패 검사(AppTest 단언, Playwright 과업 스크립트, 스크린샷 비교)로 바꾼다.

### 원칙 3. 테스트 먼저(red/green), 그리고 세션 시작은 "먼저 테스트를 돌려라"
- S16 Red/green TDD: "It's important to confirm that the tests fail before implementing the code to make them pass. If you skip that step you risk building a test that passes already"
- S16: "A significant risk with coding agents is that they might write code that doesn't work, or build code that is unnecessary and never gets used, or both. Test-first development helps protect against both"
- S16 First run the tests: "Automated tests are no longer optional when working with coding agents."
- S7: "Without tests? Your agent might claim something works without having actually tested it at all"
- S3(보안 엔지니어링 팀): "transformed their workflow from "design doc → janky code → refactor → give up on tests" to asking Claude for pseudocode, guiding it through test-driven development, and checking in periodically."

### 원칙 4. 단위 테스트 통과는 "끝"이 아니다. 실제 화면을 사람처럼 눌러 보고 증거(명령·출력·스크린샷)를 남긴다
- S16 Agentic manual testing: "Just because code passes tests doesn't mean it works as intended." / "it might crash the server on startup, fail to display a crucial UI element"
- S11: "Claude tended to make code changes, and even do testing with unit tests or curl commands against a development server, but would fail recognize that the feature didn't work end-to-end." / "Claude mostly did well at verifying features end-to-end once explicitly prompted to use browser automation tools and do all testing as a human user would."
- S14: "ask Claude for *evidence*: the command it ran and its output, or the screenshot. "All tests pass" on its own tells you very little"
- S16: Showboat의 exec 기록은 "designed to discourage the agent from cheating and writing what it hoped had happened into the document."

### 원칙 5. 만들기 전에 "완료의 정의"를 글로 고정한다(스펙). 단, 작업 크기에 맞게 가볍게
- S14: "Interview me until you could write the spec, then write it to SPEC.md." 그리고 "Once `SPEC.md` exists, start a fresh session to build from it, so the build begins with a clean context and a written definition of done."
- S4(spec-kit): "each phase has a specific job, and you don't move to the next one until the current task is fully validated." / "Crucially, your role isn't just to steer. It's to verify."
- S18(Kiro): 요구사항을 EARS "WHEN [condition/event] THE SYSTEM SHALL [expected behavior]"로 쓰고, 장점으로 "Testability : Each requirement can be directly translated into test cases"를 든다.
- 반대 근거(과설계 경고):
  - S8 Böckeler: 작은 버그에 Kiro가 "4 "user stories" with a total of 16 acceptance criteria"를 만들어 "like using a sledgehammer to crack a nut"였다. "I'd rather review code than all these markdown files."
  - S9 Thoughtworks Radar(Assess): "some generate lengthy spec files that are hard to review" / "We may be relearning a bitter lesson — that handcrafting detailed rules for AI ultimately doesn't scale."
- 적용: 화면 하나당 1쪽짜리 스펙(과업 시나리오 + EARS 몇 줄)만 쓴다. 문서가 코드보다 길어지면 멈춘다.

### 원칙 6. 한 번에 한 기능. 세션은 깨끗한 상태로 끝내고, 진행 기록과 커밋으로 다음 세션에 넘긴다
- S11: "the agent tended to try to do too much at once—essentially to attempt to one-shot the app."
- S11: "the next iteration of the coding agent was then asked to work on only one feature at a time. This incremental approach turned out to be critical to addressing the agent's tendency to do too much at once."
- S11: 기능 목록을 처음에 전부 "failing"으로 두고 "edit this file only by changing the status of a passes field"로 제한, "JSON … the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files."
- S11: 세션 시작 시 "Read the git logs and progress files", 개발 서버를 띄워 기본 E2E를 돌린 뒤 새 기능을 시작. "If the agent had instead started implementing a new feature, it would likely make the problem worse."
- S7: "Good version control habits . Being able to undo mistakes … is even more important when a coding agent might have made the changes."

### 원칙 7. 컨텍스트는 유한하다. 작업이 바뀌면 /clear, 두 번 고쳐도 안 되면 새로 시작
- S5: "context rot : as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases." / "good context engineering means finding the smallest possible set of high-signal tokens"
- S14: "Watch the first minute, press `Esc` the moment Claude drifts, and after two failed corrections run `/clear` and write a better prompt instead of a third."
- S14: "a third correction mostly adds to a conversation that already contains two failed attempts for Claude to keep re-reading."
- S14: "`/clear` between unrelated tasks. It costs nothing"
- S15 memory: CLAUDE.md는 "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence."

### 원칙 8. 일을 한 에이전트와 판정하는 에이전트를 분리하고, 판정자는 "스타일 말고 정확성"만, 그리고 사람 판정으로 보정한다
- S13: "When asked to evaluate work they've produced, agents tend to respond by confidently praising the work—even when, to a human observer, the quality is obviously mediocre."
- S13: "tuning a standalone evaluator to be skeptical turns out to be far more tractable than making a generator critical of its own work"
- S13: "Out of the box, Claude is a poor QA agent. In early runs, I watched it identify legitimate issues, then talk itself into deciding they weren't a big deal and approve the work anyway." 보정 방법: "read the evaluator's logs, find examples where its judgment diverged from mine, and update the QAs prompt"
- S14: "A reviewer that's asked to find problems will always find *something*. If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen." (그래서 리뷰 요청에 "skip style"을 빼지 말라고 한다)
- S12: "LLM-as-judge graders should be closely calibrated with human experts" / "grade each dimension with an isolated LLM-as-judge rather than using one to grade all dimensions" / "give the LLM a way out, like providing an instruction to return "Unknown""

### 원칙 9. 점수보다 "과업 통과/실패". 과업은 두 전문가가 같은 판정을 낼 만큼 분명하게, 그리고 AI 사용자는 진짜 사용자를 대신하지 못한다
- S12: "A good task is one where two domain experts would independently reach the same pass/fail verdict." / "Ambiguity in task specifications becomes noise in metrics." / "vague rubrics produce inconsistent judgments."
- S12: "20-50 simple tasks drawn from real failures is a great start." 능력 평가와 회귀 평가 구분: 회귀는 "should have a nearly 100% pass rate."
- S13: 각 기준에 "Each criterion had a hard threshold, and if any one fell below it, the sprint failed", 작업 전에 "sprint contract: agreeing on what "done" looked like for that chunk of work before any code was written."
- S13(점수 정체): "the evaluator's assessments improved over iterations before plateauing" / "I regularly saw cases where I preferred a middle iteration over the last one." / "Implementation complexity also tended to increase across rounds"
- S21 NN/g: "They often provide shallow or overly favorable feedback." / "Synthetic users seem to care about everything." / "Synthetic research cannot produce behavioral data" / "Treat the data you acquire from synthetic users as hypotheses that need testing"
- S22 NN/g: 과업은 "realistic, encourage an action, and don't give away how the interface should be used."
- S23 NN/g: "The best results come from testing no more than 5 users and running as many small tests as you can afford."

### 원칙 10. 꼭 지켜야 하는 규칙은 문장이 아니라 장치(훅·권한·CI)로. 병렬은 격리(워크트리)와 검토 병목을 같이 계산한다
- S14: "If something has to happen every time, make it a hook, a deny rule, or a managed setting. `CLAUDE.md` is for guidelines, and Claude is allowed to decide a guideline doesn't apply."
- S14: "If you keep adding emphasis to a `CLAUDE.md` line and Claude still misses it, that's a sign the line belongs in a hook."
- S14: Stop 훅은 "sends Claude back to work if the script exits with code 2." 단 "keep the enforced set small."
- S14 병렬: "give each its own checkout so the edits can't collide. `claude -w feature-auth` starts a session in a new worktree" / "A worktree is a fresh checkout, which means gitignored files like `.env` aren't there and dependencies aren't installed."
- S14: "A second session is also the easiest independent reviewer you can get."
- S6 Willison: "AI-generated code needs to be reviewed, which means the natural bottleneck on all of this is how fast I can review the results." / "I can only focus on reviewing and landing one significant change at a time" / "Code that started from your own specification is a lot less effort to review."
- S14 무인 실행 5문: "Does it know what done looks like? … Can it check its own work? … What's it allowed to touch? … What stops it? … Where does the result go, and who signs off?"

## 3. 병실관리AI 적용안

### 3.0 지금 문제를 출처에 비추어 진단

1. 점수가 안 오른 이유(추정, 근거 연결):
   - 판정이 총점(30~60점)이라 무엇이 실패인지 행동으로 정의돼 있지 않다. S12는 모호한 기준이 "noise in metrics"가 된다고 한다.
   - AI 페르소나는 "care about everything"(S21)이라 매 회차 새 지적을 만든다. S14의 "will always find *something*"과 같은 현상이다. 지적을 다 반영하면 복잡도만 오른다(S13 "Implementation complexity also tended to increase").
   - 같은 맥락에서 만든 쪽과 판정한 쪽이 겹치면 관대함·흔들림이 생긴다(S13). 사람 판정과 맞춰 본 적이 없으면 점수가 현장 판단과 같은 방향인지 알 수 없다(S12 "closely calibrated with human experts").
   - 결론: "검토 → 점수 → 전부 수정" 루프를 멈추고, "과업 계약(합격 조건) → 실패 과업만 수정"으로 바꾼다.
2. 지금 강점: pytest 1,097개, 결정적 게이트웨이, `scripts/screenshots.py`(Streamlit 띄우고 브라우저로 장면 촬영)가 이미 있다. 검사 장치를 새로 만들기보다 "과업 단위 단언"을 기존 촬영 경로 위에 얹으면 된다.

- 로그인·역할: "병동 간호사로 들어가면 다른 병동 환자 이름이 보이지 않는다" / "감염관리 담당만 격리 병상 결정 카드를 승인할 수 있다" / "권한 없는 승인 시도 시 이유가 보인다". (데모 로그인은 합성 계정이며 실제 인증 체계를 흉내 내지 않는다고 화면에 명시)
- 촘촘한 작업 목록: "한 화면(스크롤 없이 1366×768 기준)에서 오늘 퇴실 예정 전부의 다음 할 일과 지연 사유가 보인다" / "보호자 지연 건을 2클릭 안에 찾는다" / "확인 필요 판단을 되돌린다(통보 후 되돌리기, DECISIONS 2026-11-09)".
- 합격 조건은 관찰 가능한 값으로: 소요 시간 상한, 클릭 수 상한, 반드시 보여야 할 정보 목록, 보이면 안 되는 정보 목록, 에러 0.

### 3.2 검토 방식 개선: 점수제 → 과업 통과/실패 + 사람 보정

1. 판정 단위를 바꾼다
   - 총점 폐지. 과업마다 `통과 / 실패 / 판정 불가(Unknown)` 셋 중 하나(S12 "return "Unknown"").
   - 실패에는 "막힌 지점(어느 화면 요소, 무엇을 찾지 못함)"만 적는다. 개선 제안·스타일 의견은 별도 "참고" 칸, 반영 의무 없음(S14 "skip style").
   - 실패 지적만 다음 작업 목록에 들어간다. 즉 "지적의 채택 기준 = 과업 실패와 연결되는가".
2. 판정자를 분리한다
   - 만든 세션과 다른 새 세션, 읽기 전용 도구(`tools: Read, Grep, Glob` + 브라우저 실행)로(S14 reviewer.md 예시).
   - 페르소나별로 분리 판정(한 판정자가 모든 차원을 채점하지 않음, S12 "isolated LLM-as-judge").
   - 페르소나 프롬프트에는 그 역할의 "하루 업무 순서"와 "이 화면에서 반드시 끝내야 할 과업"만 준다. "몇 점인가"는 묻지 않는다.
3. 사람 판정과의 보정(처음 1회 + 화면 크게 바뀔 때)
   - 과업 10~15개를 사람(본인, 가능하면 현직자 1~2명: 기존 `docs/현직자_설문*` 경로 활용)이 직접 해 보고 통과/실패를 매긴다.
   - 같은 과업을 AI 판정자가 매기고 일치율을 본다. 어긋난 사례를 읽고 판정 프롬프트를 고친다(S13 "find examples where its judgment diverged from mine"). 일치율이 낮은 판정자는 쓰지 않는다. 일치율 목표치는 설계 가정(예: 80%).
   - AI 페르소나 결과는 "가설"로만 기록하고, 현장 수용성 주장에는 쓰지 않는다(S21). 공개 데모 문서에도 "AI 페르소나 검토는 가설 점검"이라고 쓴다.
4. 회귀 묶음으로 졸업
   - 한 번 통과한 과업은 Playwright/AppTest 회귀 테스트로 옮겨 항상 100% 유지(S12 능력 평가 → 회귀 평가 "graduate").
   - 판정 루프 상한: 같은 화면 판정 3회차까지. 3회차에도 같은 과업 실패면 과업 정의나 설계 가정을 다시 본다(S12 "0% … most often a signal of a broken task"). 이전 판이 더 나았는지 나란히 비교(S13).
5. 사람 사용성 시험은 작게 자주(S23): 화면 단계마다 3~5명(현직자 확보 어려우면 비현직 지인 + 과업 문장), "생각 소리 내기"로 막힌 곳만 기록.

### 3.3 병렬 에이전트·워크트리 규칙

1. 동시에 "합칠 구현"은 1개. 나머지 병렬은 조사, 스크린샷 촬영, 잡무(경고 정리), 독립 판정만(S6 "one significant change at a time", 조사·잡무 병렬 패턴).
2. 구현 세션은 반드시 워크트리(`claude -w <화면이름>`) 또는 `isolation: worktree` 서브에이전트. 같은 파일(`src/turnaround/ui/views.py`, `app.py`, `theme.py`)을 두 워크트리가 동시에 고치지 않는다. 화면 재설계 전에 화면별 파일 분리(페이지 단위 모듈)를 먼저 한 작업으로 끝내 두면 병렬 충돌이 준다.
3. 워크트리 준비: 새 체크아웃에는 의존성이 없으므로 설치 명령을 CLAUDE.md "명령" 절에 한 줄로(S14). `.claude/worktrees/`는 `.gitignore`(S15 worktrees).
4. 합치기 전 조건(사람이 확인): 해당 과업 테스트 green, 전체 pytest green, 스크린샷 첨부, 판정표. 한 번에 하나씩 main에 합친다.
5. 무인 실행(`claude -p`, 예약 작업)은 S14의 5문(완료 정의·자기 검사·접근 범위·중단 장치 `--max-turns`·결과 승인자)에 다 답할 수 있을 때만. 결과는 브랜치/PR로만, main 직접 푸시 금지(브랜치 보호).
6. 조사 서브에이전트의 결론은 핵심 출처를 직접 열어 확인한 뒤에만 설계에 반영(CLAUDE.md 2026-11-08 사례와 동일 원칙).

- 사람이 배포본을 직접 열어 과업 3개 수행(S16 "I like to see a feature working with my own eye before I land it").
