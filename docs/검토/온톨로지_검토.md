# 온톨로지 검토: 어떤 병원 데이터든 온톨로지로 선언해 서비스할 수 있는가

작성 2026-11-09. 사용자 질문: "어떤 병원 데이터를 넣더라도 그 병원 데이터를 온톨로지화해서 입맛에 맞춰 가공한 뒤 서비스하는 것이 목표다. 문제를 정의해 의미 계층을 주는 것이 핵심인데, 어떤 문제 해결을 목적으로 할지, 그리고 이 서비스 안에서 병원 데이터를 온톨로지로 선언하는 것이 가능한지 검토해 달라."

출처 주의: 팔란티어 공식 문서(palantir.com)는 이 세션의 네트워크 설정에서 막혀 원문을 열지 못했다. 아래 팔란티어 설명은 작업자가 이미 아는 내용이며 **원문 미확인**이다. 원문 확인이 필요하면 네트워크 허용 뒤 다시 대조한다.

## 1. 결론 먼저

1. **가능하다. 다만 "온톨로지를 병원마다 새로 만드는 것"이 아니라 "고정된 핵심 온톨로지 + 병원별 확장 + 병원 데이터 대응표(매핑)"의 3층으로 해야 한다.** 핵심 의미가 병원마다 바뀌면 안전 규칙(격리·남녀·종말소독)과 재생 증명이 성립하지 않는다.
2. **목적 문제는 하나로 좁힌다: "병상 하나가 비고 다시 차기까지(턴어라운드)의 지연과 안전 위반을 줄인다."** 온톨로지의 범위는 이 문제의 결정에 필요한 것까지다. 세상 전체를 범주화하지 않는다.
3. **지금 코드에는 팔란티어식 구성 요소(객체 종류·속성·관계·행동·기능)가 이미 다 있다. 다만 코드 여기저기에 암묵적으로 흩어져 있고, 선언된 것은 개념 계층과 안전 제약(SHACL)뿐이다.** 그래서 "선언"의 다음 단계는 새로 만드는 것보다 흩어진 것을 한 곳에 선언하고, 병원 데이터를 그 선언에 대응시키는 매핑 층을 더하는 일이다.
4. **"어떤 병원 데이터든"의 진짜 어려움은 온톨로지가 아니라 매핑이다.** 병원마다 표 이름·코드·시각의 뜻이 다르다(예: "퇴원 시각"이 오더 시각인지, 수납 완료인지, 퇴실인지. 국내 QI 자료도 기관마다 정의가 달랐다, `현장조사/제안요청서_QI_통계.md`). 이 부분을 LLM이 제안하고, 결정적 검사가 확인하고, 애매하면 사람에게 묻는 구조가 이 프로젝트의 관문 원칙과 맞는다.

## 2. 팔란티어 온톨로지의 구성 (원문 미확인)

| 구성 요소 | 뜻 | 이 프로젝트에서 이미 있는 것 |
|---|---|---|
| 객체 종류(object type) | 현실의 사물·사건 하나의 종류. 데이터 원천(표)이 뒤를 받친다 | 병동·병실·병상, 환자(합성), 퇴원 사례, 입원 요청, 매칭·확정, 청소 요청, 사람 작업, 예외 (`sim/models.py`, `saga/machine.py`) |
| 속성(property) | 객체의 값 | pydantic 필드, 이벤트 payload |
| 관계(link type) | 객체 사이 연결 | 병상→병실→병동, 퇴원 사례→병상, 입원↔병상 매칭, 재원 환자→병상 |
| 행동(action type) | 객체를 바꾸는 정해진 동작. 입력 검사·권한·부수효과를 가진다 | 게이트웨이 메서드(제안·확정·직접 수정·청소 요청·병동 이의·예외 행동 승인)와 정책 파일의 확인 등급·자율 단계 |
| 기능(function) | 객체를 읽어 계산하는 논리 | 후보 점수, 준비 시각 추정, 환기 대기, 자율권 판정, 흐름 지표 (`agent/tools.py`, `rules.py`, `forecast/`) |
| 인터페이스(interface) | 여러 객체 종류가 공유하는 모양 | 없음(필요하면 "위치를 가진 것", "기한을 가진 일") |

팔란티어는 **아무 영역**에나 이 틀을 쓰는 범용 플랫폼이다. 이 프로젝트는 **한 영역(병상 사이클)** 전용이다. 범용 플랫폼을 만들면 안전 규칙과 재생 증명을 영역마다 새로 만들어야 하므로, 앞서 사용자가 고민한 "그냥 플랫폼"보다 "영역 온톨로지 + 병원별 매핑"이 이 프로젝트의 차별점(관문과 재생 증명 내장)을 지킨다.

## 3. 문제 정의와 의미 계층

### 3.1 목적 문제
**병상 하나의 회전(퇴원 확정 → 퇴실 → 병상 준비 → 다음 환자 입실)에서 생기는 지연과 안전 위반을 줄이고, 사람은 책임질 순간에만 개입하게 한다.**

### 3.2 역량 질문 (온톨로지가 답할 수 있어야 하는 질문)
온톨로지 공학의 역량 질문(competency question) 방식으로 범위를 정한다. 아래 질문에 답하는 데 쓰이지 않는 개념은 넣지 않는다.

| 번호 | 질문 | 필요한 개념 |
|---|---|---|
| CQ1 | 이 입원 환자를 지금 안전하게 받을 수 있는 병상은 어디인가 | 병상·병실 종류·성별 운영·격리 주의·코호트·동명이인·청소 상태 |
| CQ2 | 이 병상은 언제 준비되며, 무엇이 막고 있는가 | 퇴원 단계, 단계 소요 분포, 보호자, 청소 요청·완료, 환기 대기 |
| CQ3 | 이 퇴원이 늦어지는 원인은 무엇이고 누가 풀 수 있는가 | 지연 사유, 역할, 행동 |
| CQ4 | 이 행동을 시스템이 해도 되는가, 누가 승인해야 하는가 | 행동 종류, 자율 단계, 확인 등급, 책임 역할, 근거 등급 |
| CQ5 | 늦게 온 정보가 진행 중인 어떤 일에 닿는가 | 사건의 인지 시각, 매칭 단계(연락 전·후·확정·입실), 보상 행동 |
| CQ6 | 이 병원의 규칙은 무엇이고 근거는 어디인가 | 정책 값, 근거 등급(법령·지침·병원 규정·현장 관행·설계 가정) |
| CQ7 | 어떤 유형을 에이전트에게 맡겨도 되는가 | 사람 결정 기록, 일치율, 승격 금지 목록 |

### 3.3 의미 계층

| 층 | 내용 | 병원마다 바뀌는가 |
|---|---|---|
| L0 물리 | 병동 ⊃ 병실 ⊃ 병상. 병실 종류 계층(음압 ⊂ 1인실 ⊂ 병실, 코호트 ⊂ 다인실), 공기순환 횟수 | 확장만(예: 2인실, 통합서비스 병동, 특수병실을 하위 개념으로 더함) |
| L1 역할 | 원무 배정 담당, 병동 책임간호사, 감염관리실, 미화, 약제부, 주치의. 사람이 아니라 역할 | 확장만(직영 환경관리 담당 등) |
| L2 안전 속성 | 전파경로 주의(접촉·비말·공기, 표준예방지침), 균, 선제 격리, 성별(법령) | 핵심 고정. 병원은 고위험 조건 목록만 정한다 |
| L3 과정 | 퇴원 사례 단계, 입원 요청, 매칭 단계, 청소 작업, 사람 작업, 예외. 사건(이벤트)과 상태 | 단계 순서·켜고 끄는 단계만(병원 프로필 스위치) |
| L4 결정·행동 | 행동 종류, 전제 조건(SHACL), 효과, 확인 등급, 자율 단계, 책임 행동 잠금 | 자율 단계 값만. 잠금은 바꿀 수 없다 |
| L5 정책·근거 | 규칙 값과 근거 등급 | 값은 병원마다, 법령 하한은 고정 |

**핵심 고정, 병원 확장** 원칙은 L2·L4의 안전 의미를 병원 데이터가 바꾸지 못하게 하는 장치다. 병원은 하위 개념을 더하거나 값(스위치)을 바꿀 수 있지만, 예를 들어 "음압실이 아닌 방에 공기주의 환자" 같은 위반의 뜻은 바꿀 수 없다.

## 4. 병원 데이터를 온톨로지로 선언하는 일이 이 서비스 안에서 가능한가

### 4.1 무엇을 "선언"하는가
1. **핵심 온톨로지(우리가 정의, 고정)**: 객체 종류·속성(뜻 정의 포함)·관계·행동. 지금은 `ontology/concepts.ttl`(개념 계층)과 `shapes.ttl`(안전 제약 15개)만 선언돼 있고 나머지는 코드에 있다. 한 파일에 선언하고 역량 질문을 SPARQL 시험으로 만든다.
2. **병원 확장(병원별)**: 하위 개념(그 병원의 병실 종류, 병동 특성), 병원 코드 → 개념 대응(예: 그 병원 격리 코드 "C1" → 접촉주의).
3. **매핑(병원별)**: 병원 내보내기 자료의 표·열 → 속성, 시각 열 → 사건 종류("이 열은 수납 완료 시각이다"), 단위·형식. R2RML 같은 대응표를 YAML로 둔다.
4. **병원 프로필(이미 있음)**: 절차 스위치와 값. M4 온보딩이 기록에서 초안을 만든다.

### 4.2 누가 만드는가 (CLAUDE.md 2번과의 관계)
- 매핑 초안: LLM이 표 이름·열 이름·값 표본을 보고 제안한다(판단·추출이므로 허용 범위).
- 매핑 검사: 결정적 코드가 한다. 형식·단위·필수 속성 채움률, SHACL 검사, 사건 순서 상식(퇴실이 퇴원 결정보다 앞서면 오류), 표본 재생.
- 애매한 것은 사람에게 질문(M4와 같은 방식). 확정은 사람이 한다.
- 이미 있는 비슷한 길: FHIR 이중 경로(`fhir/`, 200시드 동등성 통과)는 "표준 형식 하나에 대한 매핑"이다. 병원 전용 내보내기는 이것을 일반화한 것이다.

### 4.3 가능한 것과 어려운 것

| 가능한 것 | 어려운 것(위험) | 대응 |
|---|---|---|
| 병실·병상·병동 구조, 입퇴원 기록, 격리 오더 코드를 핵심 개념에 대응 | 같은 이름의 시각이 다른 뜻(퇴원 시각 = 오더/수납/퇴실) | 속성마다 정의를 선언하고, 매핑은 "어느 사건인가"를 명시. 순서 검사로 걸러지지 않는 애매함은 질문 |
| 병원 코드 → 개념 사전(격리 코드, 병실 등급) | 기록에 없는 사건(청소 완료 신호가 HIS에 없는 병원이 많을 수 있음) | 없는 사건은 "관측 안 됨"으로 선언하고 그 사건에 기대는 기능(준비 시각 추정)은 낮은 신뢰로 표시 |
| 병원 절차 스위치 추론(M4) | 자유 서술(원무 메모) | 추출 LLM(이미 있음) + 검사 |
| 매핑 결과를 같은 서비스·같은 안전 검사로 재생 | 데이터 품질(누락, 늦은 입력, 등록률 53% 같은 격리 등록 누락) | 품질 지표를 매핑 보고서에 넣고, 늦게 오는 정보 경로(이미 있음)로 처리 |

**실제 병원 데이터는 쓰지 않는다(CLAUDE.md 1번).** 그래서 시험은 "서로 다른 합성 병원 내보내기 형식 여러 개(열 이름·코드·시각 정의가 다름)를 넣어도 같은 서비스가 같은 결과와 같은 안전 검사를 낸다"로 한다. 이것이 "어떤 병원 데이터를 넣어도"의 시험 가능한 형태다.

### 4.4 기술 선택
- 개념 계층과 안전 제약은 지금처럼 RDF/SHACL(표준, 하위 개념 추론이 쉬움).
- 운영 객체(사건·상태)는 지금처럼 이벤트 저장소와 pydantic. 하루 재생에서 SHACL이 가장 느렸던 것처럼(검사 한 번 0.4초, 해석 재사용으로 0.03초) 모든 상태를 RDF로 옮기면 느리다. 선언은 RDF로, 실행은 코드로 하되 **선언과 코드가 어긋나지 않는지 시험으로 묶는다**(예: 선언된 객체 종류마다 코드 모델이 있는가, 선언된 행동마다 게이트웨이 메서드와 확인 등급이 있는가).

## 5. 제안: 로드맵 M6 "병원 데이터 → 온톨로지 매핑"

| 순서 | 할 일 | 끝났다고 보는 기준 |
|---|---|---|
| 1 | 핵심 온톨로지를 한 파일에 선언(객체 종류·속성 정의·관계·행동·근거 등급), 역량 질문 7개를 SPARQL 시험으로 | 질문 7개가 합성 병원 그래프에서 답을 낸다. 선언과 코드 일치 시험 통과 |
| 2 | 병원 확장·매핑 형식(YAML) | 기존 합성 병원이 매핑 파일 하나로 표현된다 |
| 3 | 서로 다른 합성 내보내기 형식 3~5개 생성기(열 이름, 코드, 시각 정의, 누락 패턴이 다름) | 형식마다 같은 숨은 병원 |
| 4 | 매핑 에이전트: LLM(시험은 가짜 LLM 결정표)이 대응을 제안 → 결정적 검사 → 질문 | 형식마다 매핑 정확도, 틀린 대응 0(애매하면 질문) |
| 5 | 매핑된 데이터로 하루 재생 | 형식이 달라도 배정·안전 검사 결과가 같다 |

M4(절차 스위치 추론)는 이 위에서 그대로 쓴다. 순서는 1 → 2 → 3·4 → 5.
