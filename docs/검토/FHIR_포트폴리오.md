# FHIR 기반 온톨로지 제안 검토: 포트폴리오 관점 (AI 엔지니어 면접관)

## 0. 전제와 현재 수준 진단
- "ai-dd"는 AI-Driven Development(명세 → 평가 → 구현을 AI 에이전트와 함께 주도)로 해석했다. "AI-Driven Design(설계 주도)"으로 읽어도 결론은 같다. 면접관은 설계를 "검증으로 닫았는가"를 본다.
- 저장소 상태(커밋 25개): 생성기, 이벤트 저장소, 사가, 게이트웨이, 최소 온톨로지(SHACL 9종)가 있고, 회귀 26/30, 홀드아웃 5/5, 테스트 약 300개다. 평가 골격 선행, 라벨 블라인드 토론, 독립 검사기, 뮤턴트 검사, 검사기와 실행기가 찾은 실제 버그 3건이 RESULTS.md에 남아 있다.
- **가장 큰 공백은 FHIR가 아니다.** `src/turnaround/agent`와 `tools`가 아직 없다. 지원 직군은 "AI 에이전트"인데 LLM 계획 에이전트, 추출, P1~P3·E1·I1 지표가 비어 있다. 지금 FHIR에 시간을 쓰면 "에이전트 없는 에이전트 포트폴리오"가 될 위험이 가장 크다.

## 1. "FHIR 기반 온톨로지"의 차별점 크기
**높게 보는 것**
- 표준 리터러시: 개념을 Location(partOf, operationalStatus v2-0116), Task(status, statusReason), Flag+SNOMED로 정확히 짚는 능력. 헬스케어 면접관은 처음 10분 안에 이것부터 확인한다.
- 표준의 빈틈을 아는 것: "R4·KR Core 1.0.2에 격리 전용 요소가 없어 Flag로 표현"은 직접 조사한 사람만 쓸 수 있는 문장이다. 이미 `docs/환자분류코드_조사.md`에 있고, 대부분의 FHIR 데모보다 낫다.
- 이식 경로: "실병원에서는 어댑터 하나만 바꾸면 된다"를 **테스트로** 보여 주면 설득력이 크다.

**의심하는 것**
- "FHIR로 저장한다"는 오해: 국내 HIS는 대부분 FHIR 원장이 아니고 FHIR는 교환 계층이다. "병원 데이터가 FHIR로 저장된다면"을 전제로 내부 모델을 FHIR에 묶으면 면접관은 표준 이해가 얕다고 본다.
- "FHIR = 온톨로지" 혼동: FHIR는 리소스 모델이고 개념 체계는 SNOMED·LOINC 몫이다. FHIR RDF(Turtle)는 장황하고, 그 위에 SHACL을 쓰면 규칙 9종이 경로 표현으로 부풀어 가독성이 떨어진다.
- 과잉 설계: 병상 24개 데모에 FHIR 서버와 RDF 정렬까지 붙이면 "이력서용 키워드 수집"으로 읽힌다.
- 데모가 실제로 도는가: 면접관은 `git clone && pytest && python -m ...`을 실제로 해 본다. Docker FHIR 서버 의존이 생기면 여기서 깨지기 쉽다.

**크기 평가:** 입력 경계 FHIR는 **중간 크기**(헬스케어 직군 서류 통과율에는 실질적 영향), 온톨로지 전면 정렬은 **작거나 마이너스**다.

## 2. 기존 AI-DD 강점과 비교한 한계 효용
이 프로젝트의 진짜 차별점은 "AI와 개발할 때 AI의 오류를 어떻게 잡았는가"의 증거다. 평가표를 구현보다 먼저 썼고, 라벨을 블라인드 토론으로 정했고, 독립 검사기가 생성기 버그(600건 중 242건 위반)를 잡았고, 뮤턴트로 평가의 민감도를 쟀고, 설계 이탈은 DECISIONS.md에 먼저 적었다. 이 수준의 AI-DD 증거를 가진 지원자는 드물다.

FHIR 작업은 이 축을 키우지 않는다. 같은 방식(명세 → 등가성 평가 → 구현)으로 하면 **같은 방법론이 표준 연동에도 통한다는 사례 하나**가 늘 뿐이다. 그래서 한계 효용은 "도메인 신뢰도"에서 나오고, 그 효용은 처음 몇 커밋에 몰려 있다. 그 뒤로는 빠르게 줄어든다. 반면 에이전트 단계(7)는 지원 직군의 핵심 역량 자체라 한계 효용이 훨씬 크다.

## 3. 범위 선택지 비교
| 안 | 내용 | 포트폴리오 효과 | 비용(커밋) | 리스크 |
|---|---|---|---|---|
| (a) 하지 않음 | 매핑 표와 조사 문서만 유지 | 현재 수준 유지. 헬스케어 면접관은 "문서로만 안다"고 본다 | 0 | 표준 실무 경험 질문에서 약함 |
| (b) 입력 경계만 FHIR | 생성기가 FHIR R4 JSON 번들(Patient, Encounter, Location 계층, Task, Flag+SNOMED)도 출력하고, 어댑터가 내부 이벤트로 바꿈 | **큼(비용 대비 최고)**. "내부 모델은 도메인에 맞게, 경계는 표준으로"라는 성숙한 아키텍처 판단을 보여 준다 | 4~6 | 낮음. 어댑터 매핑 오류는 등가성 테스트로 잡힘 |
| (c) 온톨로지까지 FHIR RDF/SNOMED 정렬 | concepts.ttl을 fhir: 네임스페이스와 SNOMED IRI에 정렬하고, SHACL을 FHIR RDF 경로로 다시 씀 | 약간 추가. 경량 정렬(`skos:exactMatch`로 SNOMED 코드만 연결)은 1커밋에 대부분의 효과가 남 | 경량 1, 전면 8~12 | 전면 정렬은 SHACL 가독성 저하, 교차 검증 재작업, SNOMED 라이선스 설명 부담 |
| (d) 전면 FHIR 서버 기반 | HAPI 등 서버를 원장으로, 구독과 If-Match 쓰기 | 키워드는 화려하지만 면접관은 운영 부담과 과잉 설계를 의심 | 15~25 | 데모 재현성 붕괴, 이벤트 소싱·사가 설계와 원장 이중화, 에이전트 단계 지연 |

참고: 설계 문서의 "PoC는 가상 FHIR 서버에 If-Match 쓰기"는 (d)의 일부다. 지금은 게이트웨이의 이벤트 순번 비교로 같은 의미를 시연하고, 서버는 DECISIONS.md에 "설계 유지, 구현 보류"로 남기는 편이 낫다.

## 4. 권고안: (b) + (c) 경량 1커밋, 단 에이전트 단계(7) 이후에
**순서:** 7단계 계획 에이전트·추출 LLM을 먼저 끝내 회귀 30/30과 P·E·I 지표 첫 값을 확보한다. 그다음에 FHIR 경계를 붙인다. 지금 해야 한다면 DECISIONS.md에 범위와 순서를 적는 1커밋까지만 한다.

**구현 범위(약 5~7커밋)**
1. DECISIONS.md: "FHIR는 교환 경계, 내부는 이벤트 소싱. 이유: 국내 HIS 원장은 FHIR가 아니며 격리는 표준에 요소가 없음." 매핑 명세(필드 단위, 미매핑 항목과 확장 필요 항목 명시)를 코드보다 먼저 쓴다.
2. 등가성 평가 먼저: "같은 시드로 내부 경로와 FHIR 경로를 돌리면 이벤트 열과 회귀 30개 결과가 같아야 한다"는 테스트를 실패 상태로 커밋한다.
3. 생성기의 FHIR R4 번들 출력. `fhir.resources` 같은 pydantic 모델이나 공식 JSON 스키마로 구조 검증하고, KR Core 프로파일 적합성은 가능한 범위까지만 검증한다고 정직하게 적는다.
4. 어댑터(번들 → 내부 이벤트). 모르는 코드는 버리지 않고 "미해석" 이벤트로 남겨 담당 검토로 보낸다. 어댑터 뮤턴트(Flag 무시, operationalStatus 오역, Task.statusReason 누락)로 회귀 시나리오가 실패하는지 확인해 기존 G4 방식을 그대로 재사용한다.
5. concepts.ttl에 SNOMED 코드를 `skos:exactMatch` 주석으로 연결한다(409524006 등). SHACL은 바꾸지 않는다.
6. 점수판에 "입력 경로(native/fhir)" 열을 추가하고 RESULTS.md에 기록한다.

**보여 주는 방법**
- README 첫 화면에 그림 하나: `HIS(가정) → FHIR R4 번들 → 어댑터 → 이벤트 저장소 → 사가/에이전트 → 게이트웨이`. 그리고 "실병원 이식 시 바뀌는 곳은 어댑터 하나"라는 문장.
- 지표 세 줄: (1) FHIR 경로와 내부 경로의 회귀 결과 일치 30/30, (2) 어댑터 뮤턴트 검출률 100%, (3) 매핑 범위(리소스 N종, 필드 M개, 표준 공백 K개와 처리 방식). 모두 "합성 데이터 기준"으로 표기한다.
- "표준의 빈틈" 섹션: 격리 요소 부재, Flag+SNOMED 선택, KR Core 1.0.2 확인 날짜. 면접 질문을 먼저 막아 주는 가장 강한 문서다.
- 의도적으로 하지 않은 것: FHIR 서버, FHIR RDF 전면 정렬. 하지 않은 이유를 적어 두면 과잉 설계 의심이 오히려 판단력 증거로 바뀐다.
- 면접 서사: "표준을 몰라서 안 쓴 게 아니라, 어디에 써야 이식성과 단순성이 둘 다 남는지 평가로 확인하고 경계에만 썼다."

**결론:** FHIR를 "하느냐 마느냐"보다 "어디까지, 언제"가 포트폴리오를 가른다. 경계 FHIR와 등가성 평가는 적은 비용으로 도메인 신뢰도를 올린다. FHIR 기반 온톨로지 전면화와 서버화는 이 프로젝트의 가장 큰 강점인 단순하고 검증된 AI-DD 서사를 흐리고, 아직 없는 에이전트 단계를 더 늦춘다.
