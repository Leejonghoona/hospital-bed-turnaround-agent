# 09. 실사용 화면 로드맵: 오류 없이 빠르게 (2026-11-10)

> 2026-11-10 사용자 결정 반영: 첫 화면 이름 "시연 화면 / 운영 화면", 화면 기술 **React 별도 웹 화면**(FastAPI + React/TypeScript/Vite), P6 사람 판정은 사용자가 직접 한다. 아래 7절의 질문은 모두 답을 받았다.

근거: `docs/검토/화면재설계/01~04`(병상관리 시스템·로그인 법령, 깃 사례, 에이전트 구현 가이드·첫 화면 모드, 바이브코딩 작업 방식). 핵심 출처는 원문을 직접 열어 확인했다. 근거를 찾지 못한 값은 "설계 가정"으로 표시한다.

## 0. 왜 다시 하는가

- 지금 화면은 "에이전트가 무엇을 판단하고 막는지 보여 주는 시연 화면"이다. 현장 페르소나 점수는 30~60점대(야간 34, 수간호사 55, 원무 62)로, "내일 써도 되는가" 기준에서 불합격이다(`docs/검토/단계검수/최고점루프_3회차.md`).
- 점수 루프가 안 올랐던 이유(04 조사 3.0): 총점은 무엇이 실패인지 행동으로 정의하지 않는다. AI 검토자는 늘 무언가를 찾고, 그 지적을 다 고치면 복잡도만 오른다(Claude Code 공식 모범 사례 "will always find *something*", Anthropic 하네스 글 "preferred a middle iteration over the last one"). 사람 판정과 맞춰 본 적도 없다.
- 그래서 방법부터 바꾼다: **점수 → 과업 통과/실패**, **전부 고치기 → 실패한 과업만 고치기**, **한 세션이 만들고 판정 → 만드는 세션과 판정 세션 분리**.

## 1. 목표 (끝났다는 정의)

| 목표 | 합격 조건(모두 통과/실패로 판정) |
|---|---|
| G1 실사용 수준 화면 | 역할별 과업 목록(아래 3절, 약 20개)이 ① 자동 과업 시험(Playwright) ② 독립 판정 세션 ③ 사람 판정(본인 + 가능하면 현직자 1~2명)에서 모두 통과. AI 판정과 사람 판정 일치율 80% 이상(설계 가정) |
| G2 현실에 맞는 접근 구조 | 개인 계정 로그인·근무 병동/역할 선택·자동 잠금·사용자 전환·접속기록 조회가 화면에 있음. 법령 최저선(01 조사 2절: 개인 계정, 최소 권한, 미사용 시 자동 차단 10~60분, 접속기록에 아이디·시각·다룬 환자·한 일)을 데모 범위에서 흉내 냄. 실제 인증 수단은 범위 밖으로 명시 |
| G3 첫 화면 모드 선택 | 첫 화면에서 "시연 화면"과 "운영 화면"을 카드로 고름(둘 다 합성 데이터). 모드는 시각 신호 2개 이상(색 띠 + 글자 꼬리표)으로 늘 보임(NN/g). 시연 화면에 운영 승인 버튼이, 운영 화면에 대본 "다음" 버튼이 없음을 시험으로 고정 |
| G4 공개 데모 | 키 없이 도는 배포본(가짜 LLM, 시작 시 합성 병원 시드 재생성)과 README 첫 화면(라이브 링크, 결과 화면 1장, 대표 시나리오 3개, "이것은 무엇이 아닌가") |
| G5 지금까지의 보장 유지 | 기존 pytest 전체 통과, 실행 상태 안전 위반 0, 최종 측정값 재현(재현 지문) |

이름 결정(사용자): **"시연 화면 / 운영 화면"**. 둘 다 합성 데이터이므로 모든 화면에 "합성 데이터 · 실제 환자 아님"을 고정 표시한다(03 조사 B-2의 오해 위험을 표시로 막는다).

## 2. 설계 결정 (조사 근거)

1. **첫 화면 = 두 카드 + 모드별 경로 묶음**(03 조사 B-3 1순위). 카드를 고르면 그 모드의 경로(`/demo/...` 또는 `/ops/...`)만 메뉴에 보인다. 의료 현장 관행은 교육 환경을 별도 인스턴스로 두는 것(Epic 운영 병원: 교육·연습 환경은 데모 환자만, 연동 없음, 모델 계정, 매일 밤 초기화 — Alberta Connect Care 원문 확인)이라, 같은 앱 안에서는 모드를 섞지 않는 쪽이 가장 가깝다.
2. **운영 화면은 로그인부터**(01 조사 4.1). 합성 개인 계정(역할·소속 병동)으로 로그인하고 근무 병동을 고른다. 모든 승인·기록에 로그인한 사람이 자동으로 남는다(지금은 승인자 ID를 입력값으로 받아 현실과 가장 어긋남). 비밀번호는 데모라도 해시로 저장하고, 공개 데모에서는 "데모 계정으로 들어가기" 버튼으로 바로 들어간다. 공용 "병동 계정"은 만들지 않는다(법령상 계정 공유 금지).
3. **작업 화면은 촘촘한 목록 + 상세 패널**(01 조사 1.2·1.4, TeleTracking 역할별 안내서). 카드 대신 한 줄 한 환자의 표(우선순위·마감·상태·다음 할 일), 줄을 고르면 옆에 상세와 처리 버튼. React 표 컴포넌트로 줄 선택·키보드 이동(위/아래, Enter로 상세)을 만든다.
4. **병상 현황판은 색과 글자 함께, 범례 고정**. 국내 표준 색은 확인되지 않았으므로(01 조사 결론 1) 국내 표준처럼 보이게 하지 않고, 해외 공개 체계(TeleTracking: 청소 대기 갈색, 청소 중 노랑, 준비 완료 녹색 등)를 참고했다고 범례에 적는다(설계 가정).
5. **사례 뷰어**(03 조사 A-3, Hamel Husain "단순한 데이터 뷰어"). 사례 ID 하나로 사건·판단 입력과 출력·게이트웨이 판정·사람 응답을 시간순 한 화면에. 감사·접속기록 조회와 같이 둔다.
6. **화면 기술은 React 별도 웹 화면**(사용자 결정, DECISIONS 2026-11-10). 도메인은 그대로 두고 얇은 FastAPI(`src/turnaround/api/`)가 기존 `ui/views.py` 화면 데이터와 게이트웨이 명령을 JSON으로 내준다. 화면은 `web/`(React 18 + TypeScript + Vite). 한 컨테이너로 배포(API가 빌드된 화면을 함께 제공). 줄 선택 표·상세 패널·키보드 조작을 웹 표준으로 만든다.
7. **시연 투어는 대표 사례 3개로**(02 조사: 잘 만든 데모는 정상·예외·안전장치가 막는 장면 3개를 대본으로). 투어는 다시 열 수 있고 진행 표시가 있다(NN/g 온보딩 글).

## 3. 과업 목록 (합격 조건의 실체)

과업은 `docs/화면재설계/tasks.json`에 둔다(id, 역할, 시작 상태 시드, 과업 문장, 합격 조건, `passes: false`). 과업 문장은 조작법을 알려 주지 않는다(NN/g 과업 시나리오). 합격 조건은 관찰 가능한 값(클릭 수 상한, 반드시 보일 정보, 보이면 안 될 정보, 오류 0)으로. 아래는 초안이고 P0에서 확정한다.

| 영역 | 과업 예 |
|---|---|
| 첫 화면 | 처음 온 사람이 3분 안에 시연 투어를 끝까지 본다 / 운영 화면을 골라 역할로 들어간다 / 투어 중 언제든 처음 화면으로 나온다 |
| 로그인·접근 | 병동 간호사로 들어가면 다른 병동 환자가 보이지 않는다 / 감염관리 담당만 격리 병상 결정을 승인할 수 있고, 아니면 이유가 보인다 / 사용자 전환 뒤 기록에 바뀐 사람이 남는다 / 내가 본 환자 기록이 접속기록에 남는다 |
| 원무 | 오늘 오전 배정할 입원 전체와 다음 할 일이 스크롤 없이(1366×768) 한 화면에 / 연락할 환자를 2클릭 안에 찾아 실제 안내 시각을 기록 / 에이전트 확정을 시한 안에 사유와 함께 되돌림 / 이전 근무에서 넘어온 일을 한눈에 구분 |
| 병동 | 내 병동 입실 예정과 준비 상태를 한 표로 / 준비 완료를 누르고 호출 보류 사유를 확인 / 배정에 이의를 낸다 |
| 감염관리 | 늦은 격리 1건을 3분 안에 결정(다시 찾기 또는 지금 병상 유지) / 종말소독 대기 병실을 찾는다 / 근무 외 시간에는 당직이 담당으로 보인다 |
| 관리자·감사 | 오늘 흐름과 안전 검사를 숫자 뜻과 함께 / 사례 하나의 판단 경과를 사례 뷰어에서 처음부터 끝까지 |
| 시연 | 대표 사례 3개(정상 배정, 안내 시각 지연 재연락, 늦은 격리를 게이트웨이가 막음)를 대본대로 / 화면마다 "이 화면에서 볼 것" |

## 4. 작업 방식 (오류 없이 빠르게)

화면 하나 = 과업 1~3개. 한 세션에서 한 묶음(①~③ 또는 ④~⑦)만 한다(04 조사 3.1).

| 단계 | 무엇 | 통과 조건 |
|---|---|---|
| ① 근거 | 그 역할의 업무 순서를 조사 기록(01)에서 찾고 없으면 조사. 근거 없으면 "설계 가정" | 화면 요소마다 근거 또는 설계 가정 표시 |
| ② 과업 | tasks.json에 과업 추가(`passes:false`) | 두 사람이 같은 통과/실패를 낼 만큼 분명 |
| ③ 1쪽 스펙 + 와이어프레임 | 5~10줄 스펙, 저해상 와이어프레임(정적 HTML 또는 그림). **사용자 확인** | 스펙 1쪽 이하, 사용자가 와이어프레임을 승인 |
| ④ 실패하는 시험 | API 시험(pytest + httpx) + Playwright 과업 스크립트를 먼저 쓰고 빨간불 확인 | 빨간불 출력 기록 |
| ⑤ 구현 | 계획 먼저, 과업 하나 = 커밋 하나 | 그 과업 시험 + 전체 pytest 통과 |
| ⑥ 화면 확인 | 스크린샷을 와이어프레임과 나란히 보고 차이 목록 | 에이전트가 이미지를 직접 열어 본 기록 |
| ⑦ 독립 판정 | 새 세션(읽기 전용)이 브라우저로 과업을 직접 수행하고 과업별 통과/실패와 막힌 곳만 보고. 점수·스타일 의견 없음 | 판정표 |
| ⑧ 기록 | RESULTS에 과업 통과 수, 사람-AI 일치, 남은 실패. 설계와 다르면 DECISIONS 먼저 | 다음 세션이 git log와 기록만으로 이어받음 |

규칙:
- **판정 루프 상한 3회**. 3회차에도 같은 과업이 실패하면 과업 정의나 설계 가정을 다시 본다(04 조사 3.2). 이전 판이 더 나았는지 나란히 비교한다.
- **실패한 과업과 연결된 지적만 고친다**. 나머지 지적은 "참고"로만 남긴다.
- **한 번 통과한 과업은 회귀 시험으로 졸업**해 늘 통과를 유지한다.
- **병렬은 조사·스크린샷·판정만**. 구현은 한 번에 하나, 워크트리에서. 같은 화면 파일을 두 곳에서 동시에 고치지 않는다(04 조사 3.3).
- **두 번 고쳐도 안 되면 새 세션**으로 다시 시작한다(맥락 오염 방지).
- **완료 보고에는 증거**(시험 출력, 스크린샷 경로, 판정표)를 붙인다.

| P4 감염관리·관리자·사례 뷰어 | 격리 결정 화면, 종말소독 대기, 관리자 흐름, 사례 뷰어·접속기록 조회 | 해당 과업 통과 | 1.5일 |

| P6 사람 판정·배포 | 사용자가 과업 10~15개를 직접 판정해 AI 판정과 일치율 기록, 소규모 사용성 시험, 한 컨테이너 배포(가짜 LLM, 시드 재생성), README 첫 화면, 포트폴리오 화면 쪽 갱신, Streamlit 화면 정리 | G1~G5 모두 통과 | 1.5일 |

합계 약 11일(설계 가정, React 전환으로 Streamlit 유지안의 약 2배). 각 단계 끝에서 스크린샷과 판정표를 보여 드리고 다음 단계로 간다. 와이어프레임(③)은 화면마다 먼저 보여 드리고 확인받는다.
