# 요구사항 보완절: SPEC과 표준 목차의 대응, 빠진 절

- 작성일: 2026-11-09. 상태: 초안 v0.2(1라운드 검수 반영).
- **SRS는 `docs/SPEC.md`(v1.0 동결)가 대신한다.** 이 문서는 SRS를 새로 쓰지 않는다. 표준 목차에 SPEC을 대 보고, 비어 있는 절만 채운다.
- **이 문서의 ID(IF-, DA-, CO-, OP-, UX-)는 기획 보완 ID이며 SPEC ID가 아니다.** SPEC에 반영되지 않았다. 대부분은 이미 구현된 것을 요구 형식으로 적은 것이다. 새 요구(상태 "공백")를 SPEC에 넣으려면 SPEC 동결 뒤 변경 절차(DECISIONS에 이유를 먼저, 버전 올림, 추적표 갱신)를 따른다.
- 설계 문서에서 "설계"·"제외"로 둔 것은 구현 범위로 쓰지 않았다. 상태 열에 그대로 표시했다. "구현(합성)"은 합성 병원의 이벤트로 동작한다는 뜻이고, 실제 병원 시스템과 연동했다는 뜻이 아니다.
- 읽는 법: ID와 근거 표시는 00 문서 0.1과 2.1을 따른다. 용어 풀이(사가, 멱등, SHACL, 홀드아웃, 뮤턴트, P10~P90, MAE 등)는 00 문서 0.3.

## 결론 먼저
1. SPEC은 기능(POL, DAT, EVT, SAG, GW, ONT, AGT, EVL, SEC), 비기능(NFR 6개), 목표 함수, 추적표를 갖췄다. 29148 SRS 목차 기준으로 **기능·보안·검증은 충분하고, 성능은 합성 규모만 확인했다**(NFR-3 측정 기록 없음).
2. 비어 있거나 약한 절은 다섯이다. **외부 인터페이스, 논리 데이터(데이터 사전·보존), 설계 제약, 운영·지원, 사용성**. 이 문서 2~6절이 채운다.
3. 새로 찾은 실제 공백은 넷이다(구현 안 됨).
   - 감사 기록 보존·파기 규칙(CO-04): 설계 문서에도 없다.
   - 정책 파일 변경 승인 절차(OP-03): 원칙("자동 범위 확대는 정책 변경 승인으로", "반영은 사람이 결정")은 설계 문서에 있고, 절차 세부(누가 제안하고 누가 승인하며 회귀를 다시 통과해야 하는지)가 없다.
   - 사용자 교육·도입 준비(OP-05): 설계 문서에도 없다.
   - 사용성 검증(UX-01): 설계 문서에 검토 카드 형식은 있으나 검증 기준이 없다.
   모두 실제 도입 단계의 일이라 프로젝트 1단계 범위에 넣지 않는다.

## 1. 대응표

### 1.1 ISO/IEC/IEEE 29148 SRS 예시 목차 ↔ SPEC
목차는 검색 요약(표준에 SRS 예시 목차가 있다는 것)과 일반 지식으로 **재구성**했다. 표준 원문과 대조하지 않았으므로 절 이름과 순서가 표준과 다를 수 있다. 그래서 번호를 붙이지 않았다.

| SRS 절 (재구성, 순서는 표준과 다를 수 있음) | 확인 수준 | SPEC의 대응 | 판정 | 보완 |
|---|---|---|---|---|
| 목적 | 요약 | SPEC 머리말, 비전 | 충분 | - |
| 범위 | 요약 | 비전 표, CLAUDE.md 4·5번, 설계 문서 "구현 범위" | 충분(흩어짐) | 04 PRD 비목표 |
| 참조 문서 | 지식 | SPEC 근거 열(설계 문서, DECISIONS, 지침) | 부분(목록 없음) | 00 문서 2절, 3절 |
| 제품 관점(시스템·사용자·하드웨어·소프트웨어·통신 인터페이스, 운영, 현장 적응) | 요약 | POS-1(보조 계층), EVT-7, SEC-1 | **부족** | 2절 IF-, 5절 OP-01(현장 적응 = 정책 파일) |
| 제품 기능 | 요약 | 1절 기능 요구 | 충분 | - |
| 사용자 특성 | 요약 | POS-4 한 줄 | **부족** | 02 페르소나 |
| 제한 사항 | 요약 | CLAUDE.md, 설계 문서 "제외" | 부분 | 4절 CO- |
| 가정과 의존 | 요약 | SPEC 1.5, DECISIONS MA- | 부분 | 05 가정 등록부 |
| 요구 배분(단계별) | 지식 | 상태 표기(구현·예정·설계·2단계) | 충분 | 04 출시 단계 |
| 기능 요구 | 요약 | 1절 | 충분 | - |
| 성능 | 요약 | NFR-3 | 부분(합성 규모만, 측정 기록 없음) | 프로젝트 2단계 이후 |
| 사용성 | 요약 | 없음 | **부족** | 6절 UX- |
| 외부 인터페이스 | 요약 | EVT-7 | **부족** | 2절 |
| 논리 데이터베이스 | 요약 | EVT-1~3 | **부족** | 3절 |
| 설계 제약 | 요약 | CLAUDE.md 기술 기본값 | 부분 | 4절 |
| 표준 준수 | 요약 | ONT-4(SNOMED 주석), EVT-7(FHIR R4), 표준예방지침 인용 | 부분 | 4절 CO-02 |
| 시스템 속성(신뢰성, 가용성, 보안, 유지보수성, 이식성) | 요약 | NFR-1·2·4·5·6, SEC | 충분 | - |
| 검증 | 요약 | 4절 추적표, `docs/평가표.md` | 충분 | - |
| 부록(용어) | 지식 | 설계 문서 용어 상자 | 충분 | 00 문서 0.3 |

### 1.2 국내 공공 SW 제안요청서 요구 분류 ↔ SPEC
분류 체계는 itwiki 등 2차 자료의 검색 요약으로 확인했다. INR의 정의는 결과에 없어 일반 지식이다. 아래 "판정"은 이 2차 자료 분류 기준으로 본 것이다.

| 분류 | 뜻 | SPEC ID | 판정 |
|---|---|---|---|
| SFR 기능 | 시스템이 해야 하는 일 | POL, DAT, EVT, SAG, GW, ONT, AGT | 충분 |
| ECR 장비구성 | 하드웨어·소프트웨어 구성 | 설계 문서 "모델"(원내 GPU 규모), CLAUDE.md 기술 기본값 | 부분(운영 장비는 모델 성능점검표 5절에서 산정 예정) |
| PER 성능 | 처리 속도, 용량, 가용성 | NFR-3, NFR-4 | 부분 |
| INR 인터페이스 | 외부 시스템·사용자 연계 | EVT-7 | **부족** → 2절 |
| DAR 데이터 | 데이터 구축·변환·보안 | DAT(합성 생성), EVT | 부분 → 3절 |
| TER 테스트 | 테스트 유형·환경·절차 | EVL, 평가표, NFR-1 | 충분 |
| SER 보안 | 접근 통제, 기밀성 | SEC-1~3, GW-7, NFR-6 | 충분 |
| QUR 품질 | 신뢰성, 사용성, 유지보수성, 이식성 | NFR-1·2·4·5 | 사용성만 부족 → 6절 |
| COR 제약 | 기술·표준·업무·법제도 제약 | CLAUDE.md, POL-2(지침 금지 조항) | 부분 → 4절 |
| PMR 프로젝트 관리 | 수행 방법, 단계 | CLAUDE.md 작업 방식, 구현 우선순위 | 충분(개인 프로젝트 수준) |
| PSR 프로젝트 지원 | 안정화, 교육, 기술 지원 | 없음 | **부족** → 5절 |
